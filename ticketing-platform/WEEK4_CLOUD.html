Reader's cheat sheet — if you read only this box

  1. Week 4 = infrastructure, not code. The services are already 12-factor (config from env, stateless, own DB, /actuator/health), so "go to AWS" is a wiring job.
  2. The path a request takes: Internet → ALB → ECS Fargate task → RDS. The ALB is the only thing the public can reach; tasks and DB live in private subnets.
  3. ECS Fargate = run containers with no servers to manage. Chosen over EC2 (too much ops) and Lambda (Spring Boot cold-start + steady load make it a bad fit).
  4. Security groups chain by id, not IP range: world → ALB SG → ECS SG → RDS SG. The DB only trusts "traffic from the ECS security group," full stop. "Who, not where."
  5. Two IAM roles per task: the execution role (pull the image + read the secret at startup) and the task role (what the running app itself may call — near-empty in Week 4).
  6. No hardcoded credentials. The DB password lives in Secrets Manager; ECS injects it into the container at start. It's never in the image or the task-def plaintext.
  7. RDS is Multi-AZ — a synchronous standby in a second availability zone, automatic failover. That's the Week-4 "managed HA" lesson.
  8. "localhost" is gone. booking → inventory was localhost:8081; on AWS it goes over the ALB path. InventoryClient's base URL is config-driven, so this is a config change, not a code change — and Resilience4j already wraps it.
  9. Everything is Terraform so the whole environment is one apply to create, one destroy to remove. Reproducible infra is the deliverable, not click-ops.

The Week-4 picture

Subnet math: 2 availability zones × (1 public + 1 private) = 4 subnets. Public = ALB + NAT. Private = ECS tasks + RDS. The database never gets a public address.

C1Why AWS now, and not in Week 1

Weeks 1–3 deliberately stayed local. The reason: debugging distributed logic (sagas, outbox, recovery) AND cloud infra at the same time is two unknowns multiplied. Get the distributed system correct on docker-compose first, then move the proven thing to AWS. Now the code is stable, so Week 4 is a pure infra exercise — and because the services are already 12-factor, nothing in them changes.

The easy-way version
Build the engine and test it on the bench (local). Only once it runs clean do you bolt it into the car (AWS). You never debug a new engine and a new car at once.
C2VPC + the security-group chain

A VPC is your own private slice of the AWS network. Inside it, public subnets can talk to the internet; private subnets can't be reached from outside. ECS tasks and RDS sit in private subnets — invisible to the world.

The real magic is the security-group chain. A security group is a stateful firewall. The trick is each layer only trusts the layer in front of it, referenced by security-group id — not an IP range:

LayerAccepts traffic from
ALB SG0.0.0.0/0 on :80 (the world — it's the front door)
ECS SGthe ALB SG, on the app port only
RDS SGthe ECS SG, on :5432 only
Why id, not IP range
"Allow the ECS security group" keeps working even as tasks scale up/down and get new private IPs. An IP/CIDR rule would either be too broad (whole subnet) or break on every scale event. It's a who rule, not a where rule.
C3IAM: two roles per task, not one

No access keys anywhere. A task proves its identity with a role. And there are deliberately two:

Execution role

Used by the ECS agent at container start — to pull the image from ECR and read the DB secret. It's "the doorman with the keys to let the app in."

Task role

The running app's own identity — what the Java process may call in AWS. Near-empty in Week 4 (the services touch no AWS APIs yet). Week 5's SQS permissions attach here, not to the execution role.

Why split them
Different lifetimes, different blast radius. If you collapse them, the app process inherits the power to pull images and read all startup secrets at runtime — far more than it needs. The split is least-privilege in action. Both policies name exact resource ARNs; no Resource: "*".
C4Fargate vs EC2 vs Lambda — the headline decision

We need to run containers. Three ways; only one fits two stateless, steady-load web services:

OptionVerdictWhy
EC2 (self-managed)✗You patch the OS, right-size the box, pack containers on it. Real control, real ops burden. Overkill here.
Lambda✗Spring Boot cold-start is seconds; these are long-lived services with a warm DB pool. Lambda wins for spiky, short, stateless work — that's the hold-expiry job later, not this.
ECS Fargate✓Stateless HTTP, steady load, want zero server management + rolling deploys + ALB health integration. Its exact sweet spot.
The one-liner for an interview
"Fargate, because they're stateless, steady-load, long-lived request/response services — Lambda's cold start and short-execution model fight that, and EC2's server management buys control we don't need. You pay a per-unit premium for no-ops; at these sizes that's worth it."
C5ALB — one front door, health-gated

The Application Load Balancer gives one stable DNS name and routes by URL path to a target group per service. It only sends traffic to tasks whose /actuator/health returns 200 — a failing task is pulled out automatically.

  • /api/inventory/* → inventory target group
  • /api/booking/* → booking target group
  • anything else → a plain 404 (an unmatched path shouldn't silently hit some service)
Classic trap to watch
A task passes its own health check but the ALB shows it unhealthy → 503s. Usual causes: wrong health-check path, wrong port, or a threshold/timeout too tight for Spring Boot's startup. First thing to verify after deploy.
C6RDS Multi-AZ + Secrets Manager

RDS is managed Postgres — no more DB dying on compose down. Multi-AZ keeps a synchronous standby in a second availability zone and fails over automatically (~60–120s) if the primary dies. Schema is still owned by Flyway (rule §3-10) — each service runs its own V1__*.sql on first connect.

During a failover
The app sees dropped connections for a beat; HikariCP (Spring's pool) reconnects to the new primary once DNS flips — no restart needed. That resilience is why Multi-AZ is worth the ~2× cost as a Week-4 lesson.
C7"localhost is gone" — the service hop

In Week 3, booking called inventory at localhost:8081. On AWS that address means nothing. Two ways to restore it:

A · via the ALB path

booking → ALB → inventory target group. One config change (base URL), reuses the LB. Costs one extra network hop of latency. Week-4 pick.

B · Service Connect / Cloud Map

Direct task-to-task DNS (inventory.ticketing.local), no LB hop. The "proper" microservice answer, more setup. A clean Phase-3 upgrade.

Why it's not scary
InventoryClient's base URL is already config-driven (inventory.base-url), so switching to the ALB path is a config value, not a code edit. And Resilience4j (timeout + retry + circuit breaker) already wraps that call — a slower ALB hop degrades gracefully instead of hanging.

AWS glossary (one line each)

VPC

Your private, isolated network inside AWS.

Subnet

A slice of the VPC tied to one availability zone; public or private.

Security group

A stateful firewall attached to a resource; rules reference other SGs by id.

NAT gateway

Lets private resources reach the internet out (pulls) without being reachable in.

IAM role

An identity a resource assumes; grants scoped permissions with no keys.

ECR

AWS's private Docker image registry.

ECS + Fargate

ECS orchestrates containers; Fargate runs them serverless (no EC2 to manage).

Task definition

The blueprint for a container: image, cpu/mem, ports, secrets, logs.

ALB + target group

L7 load balancer; a target group is the pool of task IPs it routes to.

RDS Multi-AZ

Managed Postgres with an auto-failover standby in a second AZ.

Secrets Manager

Encrypted store for credentials; injected into tasks, never in the image.

Terraform

Infra as code — declare resources, apply to create, destroy to remove.
