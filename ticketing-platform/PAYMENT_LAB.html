Reader's cheat sheet — if you read only this box

  1. Week 3 = third microservice (payment-service, port 8083) + the outbox pattern in booking-service + refund path when captured-but-confirm-fails + dangling-saga recovery sweep.
  2. payment-service uses Adapter + Factory + Strategy for the 3 stubbed gateway methods (UPI, Card, NetBanking). Adding a new method = new adapter + enum value; Factory picks it up automatically.
  3. 2-step payment (authorize then capture) makes the compensating path clean: capture-fail → void (no refund); confirm-fail-after-capture → refund. Week 2's collapsed charge() couldn't do this cleanly.
  4. Outbox defeats the dual-write problem: state change + event row commit atomically in one DB transaction; separate poller drains + publishes. Guarantee is at-least-once, so consumers MUST be idempotent.
  5. OutboxService uses Propagation.MANDATORY — refuses to run outside a transaction. That's what enforces "event row is atomic with state change." A naked call would throw.
  6. OutboxPublisher's publish runs OUTSIDE the DB transaction so a slow EventBus doesn't hold DB locks.
  7. Booking's saga recovery sweep has a 2-minute age filter — never touches a booking younger than that, so it can't race an in-flight saga. Every operation it re-drives (release, confirm, capture, refund) is idempotent by design.
  8. Payment session key = booking.idempotencyKey + "-pay" — deterministic. Recovery can look up the payment by this key OR by payment_id stored on Booking after authorize.
  9. Bug 7 caught live: Hibernate's ddl-auto: update silently skips NOT NULL columns without a DEFAULT. First booking after startup crashed with "column refund_pending does not exist." Fix in code: columnDefinition = "BOOLEAN DEFAULT FALSE". Prod-safe answer: Flyway.

The problem this week fixes

Week 2 shipped a booking saga that worked, but with two invisible cheats:
  • PaymentStub inside booking-service. Real payment is a separate concern with its own lifecycle (auth, capture, refund), separate failure modes (gateway 5xx, chargebacks), separate scaling profile. Bundling it into booking-service was the last "temporary" convenience.
  • No reliable event publishing. Week 2's saga marked CONFIRMED but nothing downstream could know — no notification service exists yet, but the mechanism for telling one didn't either. The naive "publish after commit" has a well-known dual-write failure mode.

Week 3 fixes both. Payment moves to its own container with proper lifecycle + Adapter pattern for method stubs; outbox pattern arrives to make event publishing atomic with state changes. Plus the refund path opens up (only possible with real capture semantics), and a recovery sweep closes the crash-mid-saga gap.

Why this shape — HLD

Three genuine design choices frame the whole week:

Payment as its own service

Different actors (gateway, refund ops), different failure modes (PCI-scoped, chargebacks), different scaling. Same discipline as booking-service was split from inventory.

Outbox for reliable events

Dual-write problem is real. Once booking has any downstream that cares about its state, "publish after commit" is a data-loss bug waiting to happen.

Recovery sweep, not event sourcing

Event-sourced sagas are elegant; overkill for Week 3's scale. A polling sweep with a 2-min age filter + idempotent operations gets the same crash-safety at a fraction of the machinery.

Same-process outbox poller (for now)

Debezium/CDC to Kafka is the prod-grade answer. In-process @Scheduled poller is fine for Week 3; Phase 3 swaps it for SNS with zero code change to the outbox side.

Concepts

Ten mechanisms that make Week 3 actually correct. Each = the theory + how this project uses it + a code snippet from the tree.

CONCEPT 1
Adapter + Factory + Strategy — the three-part LLD triad

Three GoF patterns applied to one problem (payment gateway integration). Each pattern earns its cost for a different concern.

PatternSolvesWhere in code
Adapter Every real gateway (Razorpay, Stripe, PhonePe) has a different wire shape. Adapter isolates payment-service's own domain from that noise. PaymentGateway interface + 3 stubs (UPIAdapter, CardAdapter, NetBankingAdapter). Each maps its native calls to authorize/capture/void/refund.
Factory Given a PaymentMethod enum from the request, resolve the right adapter without new UPIAdapter() at every call site. PaymentGatewayFactory — Spring injects every PaymentGateway bean, factory indexes them by their supports() enum.
Strategy Payment method is the caller's choice (client passes method: "UPI"). Internally, retry cadence + fallback rules can differ per gateway. Method choice = caller's Strategy. Internal per-adapter strategies (retry per gateway, fallback rules) earn a class when the second real case appears — not on day one.
The Factory bean, in real code
// PaymentGatewayFactory — indexes injected adapters by their supports() enum
private final List<PaymentGateway> gateways;   // Spring injects all three
private Map<PaymentMethod, PaymentGateway> byMethod;

private void ensureIndex() {
    if (byMethod == null) {
        byMethod = new EnumMap<>(PaymentMethod.class);
        for (PaymentGateway gw : gateways) {
            byMethod.put(gw.supports(), gw);
        }
    }
}
public PaymentGateway forMethod(PaymentMethod method) {
    ensureIndex();
    return byMethod.get(method);
}
The compiler is your ally
Add a new payment method = add enum value + write one adapter. The switch (method) anywhere in the code (if you have one) becomes a compile warning for the missing case. Factory picks up the new bean without any code change. You cannot forget to wire it up.
CONCEPT 2
Auth vs capture — why 2 steps beats 1

Real payment gateways separate authorize (reserve money, reversible) from capture (actually take money, harder to reverse). Modeling this in the stub too, because it makes the compensating path clean.

Failure branch1-step charge (Week 2)2-step auth+capture (Week 3)
Auth failsN/A (single call)No money moved → just release seats → clean rollback
Capture fails after authCharge failed = cleanVoid the auth (no refund needed, funds never moved) + release seats
Confirm fails after capture/chargeCharge already happened → refund needed (the hard case)Capture already happened → refund needed (same hard case)
The win
Only ONE branch actually needs a refund — the same one in both models. But 2-step lets the auth-succeed-capture-fail case use a cheap void instead of a full refund pipeline. Refunds settle in days; voids clear instantly.
CONCEPT 3
The dual-write problem — why "publish after commit" is a trap

booking-service marks a booking CONFIRMED and wants to notify downstreams. The naive approach:

@Transactional
public void confirm(...) {
    booking.markConfirmed();
    bookingRepository.save(booking);
    eventPublisher.publish(new BookingConfirmed(...));   // ← the trap
}
Two failure modes, both invisible
1. eventPublisher.publish(...) succeeds but the surrounding transaction then rolls back → event fired for a booking that doesn't exist. Downstream reacts to a phantom.
2. Transaction commits successfully but publish(...) throws (network drop, broker down) → booking CONFIRMED but no one knows. Notification never sent, analytics never updated.

This is the dual-write problem: you can't atomically commit to a DB AND publish to an external message broker. Ordering doesn't fix it; neither does try/catch. The bug is the shape of the code.

CONCEPT 4
Outbox — mechanics that actually defeat the dual-write

Write the event as a row in a table (outbox_events) inside the SAME transaction as the state change:

BEGIN;
  UPDATE bookings SET status = 'CONFIRMED' WHERE id = 5;
  INSERT INTO outbox_events (aggregate_id, event_type, payload, created_at)
    VALUES ('5', 'BookingConfirmed', '{...json...}', NOW());
COMMIT;

Both writes are atomic — either both commit or neither does. A separate publisher process polls the outbox_events table, publishes each unpublished row to the broker, then marks it published:

loop every 2 seconds:
    rows = SELECT * FROM outbox_events WHERE published_at IS NULL LIMIT 100
    for each row:
        broker.publish(row.event_type, row.payload)
        UPDATE outbox_events SET published_at = NOW() WHERE id = row.id
Why it survives failures
  • DB commit fails → outbox row not inserted → nothing to publish → correct
  • Broker publish fails → outbox row not marked → picked up next poll → correct
  • Publisher crashes mid-publish → some events may publish twice → consumer contract handles it (see C5)
CONCEPT 5
At-least-once delivery + the idempotent-consumer contract

Outbox gives at-least-once delivery. Not exactly-once (that's philosophically impossible in a distributed system without consumer cooperation), not at-most-once (that would mean losing events).

The contract this forces on every event consumer:

🚨 Consumers MUST be idempotent
Processing the same event twice must produce the same effect as processing it once. If your notification consumer sends an email on BookingConfirmed and the event is delivered twice, you send two emails. If your analytics consumer increments a counter, you count twice.

Deduplication belongs to the consumer — typically by tracking the event id (or aggregate id + version) and skipping duplicates.

Real prod brokers (SNS, Kafka) still give at-least-once. Consumers there face the same contract. Building consumers now that assume "exactly-once" is a future-you-hates-past-you decision.

CONCEPT 6
Why EventBus.publish(...) runs OUTSIDE the DB transaction

The OutboxPublisher.drain() method does two things per row: (1) call eventBus.publish(...), then (2) update the row's published_at. Only step 2 is inside a transaction.

for (OutboxEvent event : batch) {
    try {
        eventBus.publish(event.getEventType(), event.getPayload());   // OUTSIDE tx
        markPublished(event.getId());                                  // inside tx
    } catch (RuntimeException ex) {
        log.warn(...);                                                 // leave unpublished, next tick retries
    }
}
Why not one tx around both
If publish() takes 5 seconds (broker slow, retry backoff), holding a DB row lock for 5 seconds serializes the whole outbox. Publish is external, must never hold a DB lock. The mark-published step is fast, gets its own quick tx.
CONCEPT 7
Propagation.MANDATORY — enforcing "atomic with your business tx"

OutboxService.record(...) writes the outbox row. If called outside a transaction, it should REFUSE — because then the outbox row would commit in a separate tx, defeating the whole atomicity guarantee.

@Transactional(propagation = Propagation.MANDATORY)
public void record(String aggregateId, String eventType, Object payload) {
    ...
    repo.save(new OutboxEvent(...));
}
MANDATORY vs REQUIRED
REQUIRED would start a new transaction if none exists — silently defeating the atomicity guarantee. MANDATORY throws an IllegalTransactionStateException if there is no active transaction. The failure is loud and immediate. Anyone who calls this without wrapping in @Transactional or a TransactionTemplate finds out on the first call, not in production.
CONCEPT 8
Refund path — the hard case in every distributed saga

Money captured (CAPTURED), but inventory /confirm then failed. Booking-service must:

  1. Call paymentClient.refund(paymentId, ...) — try to unwind the capture
  2. If refund succeeds → mark booking FAILED (money returned, cycle complete)
  3. If refund fails (Resilience4j retries exhaust) → mark FAILED_REFUND_PENDING (ops queue picks it up)
private boolean tryRefund(Long paymentId, Long bookingId) {
    try {
        paymentClient.refund(paymentId, "booking " + bookingId + " confirm failed after capture");
        return true;
    } catch (RuntimeException ex) {
        log.warn("saga_refund_failed paymentId={} bookingId={} reason={}", paymentId, bookingId, ex.getMessage());
        return false;
    }
}
The distinction that matters
FAILED and FAILED_REFUND_PENDING are both terminal. But the ops team's queue query is WHERE refund_pending = true. Without the distinct flag, a plain FAILED with money still held wouldn't surface — a lost booking, a customer waiting for refund, no ticket in your issue tracker.
CONCEPT 9
Dangling-saga recovery — the age filter that prevents self-races

booking-service crashes mid-saga. Some booking is stuck in PENDING / SEATS_HELD / PAYMENT_INITIATED. Nobody drives it forward. The BookingRecoveryService @Scheduled sweep picks it up.

@Scheduled(fixedDelayString = "${booking.recovery.sweep-interval-ms:60000}")
public void sweep() {
    Instant olderThan = Instant.now().minus(Duration.ofMinutes(2));   // AGE FILTER
    List<Booking> dangling = bookingRepository.findDangling(
            List.of(PENDING, SEATS_HELD, PAYMENT_INITIATED),
            olderThan);
    for (Booking b : dangling) {
        recover(b);
    }
}
Without the 2-minute age filter
A booking created 10 seconds ago is probably still executing right now in some request handler's saga. The sweep would race it — both trying to /confirm or /capture, both trying to write the same state change. Interleaved failures, undefined outcomes. The sweep must NEVER touch a booking younger than the saga could plausibly still be running.
Idempotency of every re-driven operation
Every op the sweep calls is idempotent by design: /release is a no-op if already released, /confirm returns the same response for a retry, payment /capture returns CAPTURED either way, /refund returns REFUND_PENDING either way. Safe to re-drive from any state.
CONCEPT 10
Deterministic session key — the recovery bridge

When booking-service calls POST /payments, it passes paymentSessionKey = booking.idempotencyKey + "-pay". Deterministic per booking. That means:

  • A retry of the same booking sends the SAME session key → payment-service returns the SAME payment (idempotency)
  • The recovery sweep can look up the payment by sessionKey if payment_id wasn't stored yet (e.g. crash between insert and payment_id write)
  • The two services share no state directly — the key is the only bridge, and it's mathematically derivable from data both already hold
Why not a UUID
A random UUID would work for idempotency but not for recovery — if the booking service loses the payment_id (crash before markPaymentInitiated), it also lost the UUID → payment now orphaned. Deterministic keys are recoverable from booking's own data.

DAY 6
MDC survives the @Scheduled boundary — carry the id on the row
updated: outbox/OutboxEvent, OutboxService, OutboxPublisher · commit: 8a30afa

The real pattern lesson hiding behind Day 5's null-correlation-id observation.

🐛 Root cause — MDC is thread-local, @Scheduled is a different thread
booking-service's saga runs in the request thread. CorrelationIdFilter set MDC there. OutboxService.record() inherits it (same thread). BUT OutboxPublisher.drain() runs in a @Scheduled thread from Spring's task scheduler pool — different thread, empty MDC. So EventBus.publish() read MDC and got null. RestClient's requestInterceptor added no X-Correlation-Id. Notification-service's own filter generated a fresh UUID → trace context lost at the outbox boundary.
✅ Fix — carry the id on the row itself
  1. OutboxEvent entity gains a correlation_id VARCHAR(64) column (nullable). Constructor updated.
  2. OutboxService.record() captures MDC.get(correlationId) at write time (still on the request thread with populated MDC) and stores it on the row.
  3. OutboxPublisher.drain() reads the row's correlation id, MDC.puts it before eventBus.publish(), clears in finally.

Now the notifications.correlation_id column stores the SAME id booking-service used at record time. Full trace across booking → outbox → poller → HTTP → notification.

💡 The general pattern

MDC drops across every async boundary — @Scheduled thread pool, CompletableFuture.supplyAsync, reactor's subscribeOn/publishOn, JMS listener threads. Fix is always the same: carry the id on the payload, restore on the other side. Not a one-off, a fundamental async-plumbing rule that will re-appear every time an async hop is added to this codebase.

Live-verify not re-run for this fix — mechanism proven by three-file inspection; end-to-end test at the next fresh docker compose up will show notifications.correlation_id populated instead of null. Deferred to save Docker daemon churn on this fragile machine.

Bug museum — four real ones caught live

BUG 7
Hibernate ddl-auto: update silently skips NOT NULL column with no DEFAULT
Symptom (live-verify moment)
Services all started, health checks green. First POST /bookings after startup: HTTP 500 — An unexpected error occurred. Logs showed: ERROR: column b1_0.refund_pending does not exist. \d bookings in psql confirmed: payment_id (nullable Long) was added, but refund_pending (NOT NULL boolean) was NOT.
Root cause
Hibernate's ddl-auto: update tries to ALTER TABLE bookings ADD COLUMN refund_pending BOOLEAN NOT NULL. Postgres refuses that DDL — you cannot add a NOT NULL column to a populated table without a DEFAULT value (existing rows would have NULL). Hibernate swallows the DDL error and starts anyway. The entity mapping still references the column, so at first SELECT, Hibernate looks for a column Postgres doesn't have. Boom.
Fix — columnDefinition for the default
@Column(name = "refund_pending", nullable = false,
        columnDefinition = "BOOLEAN DEFAULT FALSE")
private boolean refundPending = false;
Hibernate now emits ALTER TABLE ... ADD COLUMN refund_pending BOOLEAN NOT NULL DEFAULT FALSE which Postgres accepts. Live fix during the verify session: manual ALTER TABLE ... ADD COLUMN ... DEFAULT FALSE via docker exec psql. Immediate; retry succeeded.

The lesson worth keeping: ddl-auto: update is not production-safe. Flyway/Liquibase writes explicit ALTER statements with proper DEFAULT clauses that work on populated tables. Yet another reason to migrate to migrations for real deployments.

BUG 8
Bug 4 re-strikes — Postgres init script skipped again
Symptom
Started Postgres for live-verify. \l showed booking + inventory databases but NO payment. The db-init/create-payment-db.sh script I'd just added never ran.
Root cause + fix (SAME as Bug 4 from Week 2)
Postgres image runs init scripts only on first container start against an empty volume. The pgdata volume was created back in Week 2's live-verify; adding a new init script two weeks later doesn't retro-run against the populated volume. Live fix: manual CREATE USER payment_user; CREATE DATABASE payment OWNER payment_user; via docker exec psql. Same workaround as Bug 4 documented; same prod-safe answer (Flyway).

The re-strike is worth noting: the fix isn't in the compose file — it's in switching off ddl-auto + init scripts entirely and using Flyway. That work is deferred, so this bug will re-strike every time a new service DB is added. Documenting so a fresh session doesn't spend an hour debugging why the DB is missing.

BUG 9
Java's public-class-in-matching-filename rule
Symptom
First compile of payment-service failed: class AuthResult is public, should be declared in a file named AuthResult.java. I'd put the AuthResult record inside a file called GatewayResponse.java.
Root cause + fix
Java rule: a public top-level class or record MUST be in a file matching its name. Non-public (package-private) can live anywhere. Fix: renamed the file to AuthResult.java, deleted the GatewayResponse.java stub. Trivial fix, easy to overlook when scaffolding fast.
BUG 10
YAML duplicate-key trap (application.yml)
Symptom (near-miss, caught during editing)
Editing application.yml to add a second Resilience4j instance for payment, I accidentally nested a new retry: / circuitbreaker: hierarchy at the wrong indent. Result: two circuitbreaker: keys under resilience4j:. YAML parsers handle this differently — some silently take the last one; others throw. Spring's would have silently dropped the inventory CB config.
Fix — rewrote the whole block clean
Rather than patching the nested mess, I rewrote the resilience4j: section from scratch with proper structure: one retry.instances block with both inventory + payment children, one circuitbreaker.instances block with both. Caught before running (compile would not have caught this — only actual runtime behavior would).

Lesson: multi-level YAML edits benefit from a full-file view. In-place patches into deeply nested config are one of the few places Edit is more error-prone than Write. Same trap for anyone editing application.yml to add a second Resilience4j / logging appender / Spring Data source.

Decision log — A over B

Every real decision has an obvious-looking B. Here's why we didn't pick it.

DECISION
Payment as separate service, not @Service PaymentService in booking

Why not keep as an internal service class: genuine ownership boundary. Different actors touch it (payment ops, gateway integration, compliance), different scaling profile, different failure modes. Bundling means every one of those concerns pulls in booking-service's whole context.

DECISION
Outbox pattern, not "publish after commit in same method"

Why not just call publisher.publish(...) after @Transactional commits: classic dual-write problem. Publish before commit = phantom events for rolled-back state. Publish after commit = lost events on network failure. Outbox is the only pattern that gets both cases right, and the DB is the atomicity boundary that makes it work.

DECISION
Same-process poller, not Debezium/CDC to Kafka

Why not the prod-grade answer now: Kafka + Debezium is a big infra bet. In-process poller works fine at Week 3 scale (~seconds of latency, single-service outbox). Phase 3 introduces real messaging (SNS/SQS); at that point the poller becomes an SNS publisher — same outbox side, different sink.

DECISION
Recovery sweep, not event-sourced saga

Why not store each saga step as an event and replay: event-sourcing is the beautiful answer but 5× the code and requires operational buy-in (event store, snapshotting, projection versioning). Polling sweep + idempotent operations gets the same crash-safety with tools we already have (Postgres + @Scheduled).

DECISION
Two independent Resilience4j instances (inventory, payment), not one shared

Why not one "outbound" instance: payment being unhealthy would open inventory's circuit too. Cross-dependency false coupling. Independent instances = independent health signals; each dependency's problems stay contained.

DECISION
Copy PaymentClient's fallback + retry config from InventoryClient, not extract

Why not a shared "ExternalClient" superclass: the two clients have different endpoints, different exception types, different Resilience4j instance names. What's shared is the pattern, and patterns don't belong in inheritance — they belong in documentation. Duplication is cheap; wrong inheritance forces both to change together.

DECISION
Hardcoded price stub (₹500/seat), not a Pricing service

Why not a real pricing service now: pricing is a Phase 2 concern per ROADMAP. Week 3 is about payment lifecycle, not price discovery. Stub with a comment pointing to the deferral. Real pricing service replaces the constant when it arrives; the saga's shape doesn't change.

DECISION
Delete BookingSagaServiceTest (junits deferred), not update it

Why not port the old test to the new saga shape: user's explicit no-junits-during-implementation directive. The saga's behavior changed enough (PaymentStub gone, 2-step payment, refund path, outbox event) that the old test would be a full rewrite anyway. End-of-week clean-pass will build proper tests over the finished shape.

Tech glossary — new things this week

Two sentences per item: what it is + the specific problem it solves in this project.

Adapter pattern

Interface that hides gateway-specific wire shapes. Solves: payment-service's own domain stays clean; adding a new real gateway = one new class.

Factory (with Spring DI)

Resolves the right adapter for a given PaymentMethod from injected beans. Solves: no new UPIAdapter() at call sites; adding a method never touches the factory's logic.

Two-step auth + capture

Separate authorize (reserve, reversible) from capture (take, harder to reverse). Solves: cheap void for auth-succeeded-capture-failed; only true refund for confirm-failed-after-capture.

Outbox pattern

Table that stores events written atomically with state changes; separate poller drains. Solves: the dual-write problem — DB commit + event publish can't be one atomic op, but DB commit + outbox row insert CAN.

At-least-once delivery

The realistic guarantee any distributed message system can offer. Solves: loss avoidance; forces consumer contract to be idempotent by design.

Propagation.MANDATORY

Spring transactional propagation that refuses to run outside a tx. Solves: enforces "outbox row commits with your business tx" at Spring level, not by hopeful convention.

@Scheduled + @EnableScheduling

Spring's built-in cron/interval scheduler. Solves: the outbox poller + recovery sweep + auth-expiry sweep all run without a separate scheduler infrastructure.

Saga recovery sweep

Polling job that finds crashed sagas and drives them forward or rolls them back. Solves: the "process crashed mid-flight" gap that idempotency alone can't close.

Age filter (2-minute rule)

Sweep only touches records older than N minutes. Solves: sweep-vs-in-flight-saga race — a saga started 10 seconds ago is probably still executing; leave it alone.

Deterministic session key

Key derived from stable data (booking's idempotency key + suffix) instead of random UUID. Solves: recovery can look up payment even if the payment_id was never written back to booking (crash between insert and update).

ProblemDetail (RFC 7807)

Machine-parseable error envelope with title + status + detail + custom fields. Solves: consistent error contract across all three services now.

Correlation ID propagation over REST

Client passes / server generates + echoes / outgoing calls forward via X-Correlation-Id. Solves: one grep across three services' logs reads as one story for a single booking.
