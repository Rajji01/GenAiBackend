The one scenario every section below refers back to

Two people tap "book" on the same seat, at the same instant, from two different phones. Exactly one of them must get it. The other must see a clean, honest "someone else got there first" — not a crash, not a double-booking, not a seat that silently vanishes from the system. Every mechanism on this page exists to make that true, and to make an abandoned attempt clean itself up automatically a few minutes later.

HLD

Why a dedicated inventory-service, and why two stores

The rest of the ticketing platform (catalog, booking, payment, notifications) doesn't exist yet — by design, Week 1 builds exactly one service, all the way to production-hardened, before adding a second. Two high-level decisions shape everything below:

Why inventory is its own service

Seat availability is read constantly (every visitor browsing a show) and written rarely but contentiously (a burst of holds on a popular show's release). That read/write shape, and its scaling profile under a flash-sale spike, is completely different from booking orchestration or payment retries — bundling them into one service would mean scaling the wrong thing under load.

Why two stores, not one

Postgres is durable but has no native "expire this row after 5 minutes" primitive. Redis has TTL natively but nothing stops two unrelated write paths from touching the same row underneath it. Neither store's strengths cover the other's gap — so both are used, each for the one job it's actually good at. See Concept 3.

Concepts

The theory behind every "why" below

Eight mechanisms, explained twice each: what the idea is in general (the theory an interviewer would expect), and exactly how inventory-service uses it (the implementation an interviewer would probe next).

CONCEPT 1 Optimistic vs. pessimistic locking

The general theory

Two transactions both want to touch the same row. There are exactly two philosophies for stopping them from corrupting each other:

Pessimistic

SELECT ... FOR UPDATE — grab a real database lock on the row the moment you read it. Every other transaction wanting that row simply waits until you commit or roll back. Correct by construction, but every waiter is now blocked in real time — expensive under contention, and a slow holder stalls everyone behind it.

Optimistic

Don't lock anything. Read the row, remember the version number you read it at, do your work, then write back with WHERE id=? AND version=?. If nobody else touched the row, the version still matches and your write succeeds. If someone else won the race, zero rows match your WHERE clause — your write silently updates nothing, and the ORM turns that into an exception you can catch.

Optimistic locking is the right default when conflicts are rare relative to reads — most seats, most of the time, are not being fought over. Pessimistic locking earns its cost when conflicts are common and blocking is cheaper than retrying (e.g. a single global counter every request touches).

How this project actually does it

@Entity
public class Seat {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private SeatStatus status;

    @Version
    private Long version;   // <-- this one annotation is the whole mechanism
}

Hibernate does three things with that single @Version field, entirely on its own:

  1. Every SELECT against this entity also fetches version.
  2. Every UPDATE Hibernate generates includes AND version = ? in its WHERE clause, using the value that was read — and sets the new row's version to current + 1.
  3. If the driver reports zero rows affected by that UPDATE (because some other transaction already bumped the version), Hibernate throws OptimisticLockingFailureException instead of silently doing nothing.
-- what Hibernate actually sends for HoldService granting a hold: UPDATE seats SET status = 'HELD', version = 2 WHERE id = 7 AND version = 1; -- if a concurrent request already moved this row to version 2, -- the WHERE clause matches nothing → 0 rows updated → exception.

This is why HoldService never has to write a manual if (someone else has it) throw check for the Postgres side — the version column enforces it at the SQL level, for every writer, including code that doesn't even know about the hold flow.

Why optimistic, here specifically

A given seat is contended by at most a handful of concurrent requests, for a few hundred milliseconds, during the specific moment someone clicks "hold." Pessimistic locking would mean every hold attempt blocks on a real database lock even when there's no actual conflict 99.9% of the time — optimistic locking pays nothing when there's no conflict, and only pays a retry (or a clean 409) on the rare occasion there is one.

CONCEPT 2 Redis SETNX + TTL, as a distributed lock

The general theory

SETNX key value ("SET if Not eXists") is atomic at the Redis server level: if the key is absent, it's created and the command returns success; if it already exists, nothing changes and the command reports failure. Because Redis processes commands single-threaded, there is no window where two clients can both "win" — this is exactly a mutual-exclusion lock, implemented as one atomic server-side operation instead of application-level coordination.

The missing piece a plain lock always has is cleanup: if the process holding the lock crashes, or a network partition eats its "I'm done" message, the lock is held forever. Redis's EX (expire) option attached to the same atomic command solves exactly that — the key deletes itself after N seconds with zero additional code, zero cron job, zero "did the cleanup job run" anxiety.

How this project actually does it

Boolean acquired = redisTemplate.opsForValue()
        .setIfAbsent("hold:" + seatId, holderId, Duration.ofSeconds(300));
// true  -> we now own this seat's hold, for up to 5 minutes
// false -> someone already holds it (check who, below)

setIfAbsent(key, value, ttl) is Spring Data Redis's name for the atomic SET key value NX EX 300 command — one round trip, one atomic decision, TTL attached from the start (not set in a second call, which would leave a tiny window where the key exists with no expiry if the process died between the two calls).

key = hold:<seatId> value = holderId TTL = inventory.hold.ttl-seconds (300)
Why the value is the holderId, not a random token

Storing the requester's own id as the lock's value (instead of a server-generated opaque token) means a retry by the same caller can be recognized as a retry, not a conflict — reading the key back and comparing it to the incoming holderId is the entire idempotency check (see Concept 4). No separate "who owns this lock" table needed.

CONCEPT 3 Two-store coordination & compensating actions

The general theory

The moment a "transaction" spans two different data stores that don't share a commit protocol, you lose the atomicity a single database gives you for free. Redis and Postgres cannot both commit or both roll back as one unit — there is a real window between "Redis says yes" and "Postgres says yes" where the system is in an intermediate state. The standard answer, borrowed from the saga pattern used across microservices, is: don't prevent the intermediate state, detect and compensate for it. If step 2 fails after step 1 already succeeded, explicitly undo step 1 rather than leaving it dangling.

How this project actually does it

Boolean acquired = redisTemplate.opsForValue().setIfAbsent(key, holderId, ttl);
if (Boolean.TRUE.equals(acquired)) {
    try {
        // ...Postgres @Version update...
    } catch (RuntimeException ex) {
        redisTemplate.delete(key);   // <-- the compensating action
        throw ex;
    }
}

Step 1 (Redis SETNX) succeeds first. If step 2 (the Postgres update) then fails for any reason — the seat doesn't exist, it's already booked, or a genuine optimistic-lock conflict — the catch block deletes the Redis key before re-throwing. Without this, a request that failed at step 2 would still leave the seat looking "held" in Redis for up to 5 minutes, with no actual hold behind it: a phantom lock nobody could break except by waiting out the TTL.

The failure mode this specifically prevents

Client sends a hold for a seat that's already BOOKED in Postgres, but nothing is currently in Redis for it (maybe a previous hold's TTL already expired and reconciliation hasn't swept yet). Redis SETNX succeeds — the key didn't exist. The Postgres check then finds status=BOOKED and throws. Without the compensating delete, that seat would show as "held" to every other client for up to 5 minutes, even though the actual attempt failed and nobody holds it.

CONCEPT 4 Idempotency: same request twice, one effect

The general theory

A network call can fail after the server did the work but before the client saw the response — the client has no way to tell "it never happened" apart from "it happened but I didn't hear back." The only safe client behavior is to retry. The only safe server behavior, then, is to make retrying the exact same request produce the exact same end state as doing it once — not a second seat held, not a second charge, not an error that implies something went wrong when nothing did.

How this project actually does it — two different shapes, on purpose

Hold: idempotent by recognizing the retry

If hold:{seatId} already exists, HoldService reads the stored value back. If it equals the caller's own holderId, this is the same caller asking again — return the same success response, touch nothing in Postgres a second time. A different holderId, by contrast, is a genuine conflict (409).

Release: idempotent by treating "already done" as success

If no hold exists for the seat at all — already released, or the TTL beat the caller to it — release() simply returns. The end state the caller wanted (no hold on this seat) is already true. There's no reason to fail an operation whose entire goal has already been achieved.

Two different mechanisms, same principle: judge idempotency by comparing to the end state the caller wants, not by whether this exact code path has run before.

CONCEPT 5 RFC 7807 ProblemDetail & centralized exception handling

The general theory

RFC 7807 is an actual IETF standard for what an HTTP API error body should look like — a consistent JSON shape (type, title, status, detail) instead of every endpoint inventing its own. Spring's ProblemDetail class produces exactly this shape. Pairing it with @RestControllerAdvice means exception-to-HTTP-status mapping happens in one place for the whole application — no controller method needs its own try/catch, and every 4xx/5xx response looks the same to every client.

How this project actually does it

ExceptionStatusMeaning
ResourceNotFoundException404Seat, or seat-under-this-show, doesn't exist.
ConflictException409The resource's state disagrees with the request (already held, already booked).
ForbiddenException403The resource is fine — you just don't own this hold.
OptimisticLockingFailureException409Hibernate's own exception when a version check fails — mapped the same way as a business-level conflict.
MethodArgumentNotValidException400A @Valid DTO failed field validation (e.g. blank holderId).
Exception (anything else)500Logged in full server-side; the client only ever sees a generic message — the real exception text is never leaked.
Why 403 is a separate class from 409

409 means "try again differently, the resource state changed." 403 means "nothing about the resource is wrong — you specifically are not allowed this action." Collapsing both into one exception type would tell a client the wrong thing to do next: retrying a forbidden release will never succeed no matter how many times you try, unlike a real conflict.

CONCEPT 6 MDC & correlation IDs

The general theory

In production, one server handles thousands of interleaved requests on a shared thread pool — a plain log file is a single stream where every request's lines are shuffled together with every other request's. A correlation ID is a value generated (or received from an upstream caller) once per request and attached to every log line written during that request, so a human — or a log-search query — can pull out exactly one request's story from the noise. MDC (Mapped Diagnostic Context) is SLF4J's mechanism for this: a thread-local map that the logging pattern can read from automatically, without passing the ID as a parameter to every single log call.

How this project actually does it

String correlationId = request.getHeader("X-Correlation-Id");
if (correlationId == null || correlationId.isBlank()) {
    correlationId = UUID.randomUUID().toString();
}
response.setHeader("X-Correlation-Id", correlationId);
MDC.put("correlationId", correlationId);
try {
    chain.doFilter(request, response);
} finally {
    MDC.remove("correlationId");   // <-- not optional
}
Why the finally block is load-bearing, not defensive style

Tomcat's request-handling threads are pooled and reused. If MDC.remove is skipped (an early return, an uncaught throw before cleanup), the next, completely unrelated request that happens to land on the same pooled thread would silently inherit this request's correlation id in its own logs — a real, hard-to-notice bug, since logs would look normal, just wrong.

Reading the incoming header (not always generating a fresh one) is what makes this a real building block for distributed tracing later: once booking-service exists and calls inventory-service, the same correlation id can be threaded through both services' logs for one end-to-end user action.

CONCEPT 7 Testcontainers instead of H2 / embedded fakes

The general theory

A common shortcut for "fast" tests is swapping the real database for an in-memory one (H2 pretending to be Postgres) or an embedded fake (a Java-only Redis stand-in). These start fast and need no Docker — but they don't behave identically to the real thing: SQL dialect differences, constraint-enforcement differences, and — critical for this project — optimistic-locking and unique-constraint behavior that can silently differ between H2's Postgres-compatibility mode and real Postgres. Testcontainers instead starts the actual Postgres and actual Redis Docker images for the test run, then throws them away — slower per run, but testing the real thing.

How this project actually does it

@DataJpaTest
@AutoConfigureTestDatabase(replace = AutoConfigureTestDatabase.Replace.NONE)  // <-- the line that matters
@Testcontainers
class SeatRepositoryTest {
    @Container
    static PostgreSQLContainer<?> postgres = new PostgreSQLContainer<>("postgres:16-alpine")...

@DataJpaTest silently swaps in H2 by default unless replace = NONE is specified — an easy, invisible mistake that would have quietly defeated the entire point of this project's test suite. HoldServiceTest goes further and boots real Postgres and real Redis together in the same test, since the bug that class exists to prevent (a Redis lock outliving Postgres state) can only be reproduced when both stores are the real coordination-sensitive thing, not a fake of either.

The concrete cost/benefit, from this project's own numbers

The full 30-test suite (six Testcontainers-backed classes, several booting a full Spring context against fresh Postgres+Redis containers) takes 2-4 minutes to run — noticeably slower than an H2-backed suite would be. That cost was accepted deliberately: this service's entire reason to exist is behavior (locking, constraints, TTL expiry) that a faster fake cannot faithfully reproduce.

CONCEPT 8 Spring config layering — profiles, properties, and how they silently break

The general theory

Spring Boot resolves application.yml from the classpath. When several JARs or source roots each contribute a file with that exact name, the classloader resolves classpath:/application.yml to exactly one of them — not a merge of all of them. Profile-specific files (application-<profile>.yml) work completely differently: they only load when that profile is explicitly active, and when they do, Spring layers them on top of the base file, with the profile's values overriding just the keys it defines — everything else from the base file survives untouched. Confusing the two mental models (same-name replacement vs. profile-name layering) is a very easy, very silent mistake.

How this project actually does it (after getting it wrong once — see Bug Museum #2)

src/main/resources/application.yml

The real config: datasource, Redis, ddl-auto: update, the logging pattern, and sensible dev defaults for every inventory.* property.

src/test/resources/application-test.yml

Loaded only by classes carrying @ActiveProfiles("test"), and only overrides inventory.reconciliation.enabled: false — everything else still comes from the base file, correctly merged.

@ConfigurationProperties (InventoryProperties) is the other half of this concept: it gives application code a typed, validated view of one property subtree, instead of scattering raw ${inventory.hold.ttl-seconds:300} placeholder strings through business logic. A typo in a bound property name fails loudly at startup; a typo inside a placeholder string just silently returns the default forever.

DAY 3 Hold, release & reconciliation
HoldService.java · HoldReconciliationService.java · HoldController.java · GlobalExceptionHandler.java · exception/*.java

The concurrency heart of the whole platform. See Concept 1, Concept 2, Concept 3, and Concept 4 — everything in HoldService is one of those four ideas, wired together.

The open question Day 1's README explicitly flagged, closed here

If a hold's Redis TTL expires with nobody calling /release (the common case — an abandoned checkout), what reverts the Postgres row from HELD back to AVAILABLE? Nothing, until HoldReconciliationService: a @Scheduled polling sweep, checked against real Redis rather than trusted blindly, that finds every HELD seat whose Redis key is already gone and reverts it.

Why polling, not Redis keyspace-notification pub/sub

Redis can publish an event the instant a key expires — tempting, since it means zero polling delay. But pub/sub delivery in Redis is fire-and-forget: a notification published while the app was mid-restart is gone forever, no replay, no queue. A seat that missed that one notification would stay HELD permanently. A periodic sweep is slightly less immediate but self-heals even after a missed event — the right trade for correctness over latency here.

DAY 5 The failure experiment — automated, then live
ConcurrentHoldFailureExperimentTest.java

Every earlier test called things one at a time. This is the one day whose entire point is making two callers race for real — a CountDownLatch holds both threads at the starting line and releases them together, as close to simultaneously as the JVM allows.

Test 1 — the real flow

Two threads call HoldService.hold() for the same seat. One gets a HoldResponse, the other a ConflictException — every single run, not "usually."

Test 2 — Postgres alone, Redis bypassed entirely

Two threads call seatRepository.save() directly, skipping HoldService and Redis completely. This is the one true proof of Concept 1 in isolation — exactly what Day 2 explicitly deferred, since it needs real threads.

A genuinely useful thing this revealed

In the normal /hold flow, it's Redis's single-threaded SETNX that actually resolves the race in practice — one caller's key-set wins, the other fails the check and gets a clean ConflictException before Postgres is ever touched. Postgres's @Version is not a redundant no-op sitting behind it, though: Test 2 proves it independently holds the line even with Redis completely out of the picture — the safety net for any write path that isn't going through HoldService's Redis gate at all (a future service, a manual fix, a bug in the Redis check itself).

Bug museum

Real failures, kept on purpose

Not mistakes to be embarrassed about — evidence that the tests were actually exercising something real. Each one changed how a later part of this project was built.

BUG 1 A live scheduler outliving its own Testcontainers
What happened

The moment HoldReconciliationService's @Scheduled method existed, every @SpringBootTest in the suite silently gained a live background timer. Test classes run sequentially, each starting and stopping its own Testcontainers Postgres/Redis. A scheduled sweep from one test class's context fired after that class's containers were already torn down, hit a dead Postgres port, and logged a raw "Connection refused" — even though every actual test assertion still passed.

The fix

Gate the whole bean behind @ConditionalOnProperty(inventory.reconciliation.enabled), default true in real config but false for the entire test module — so the bean simply doesn't exist in most tests. The one test class that actually needs it (HoldReconciliationServiceTest) explicitly re-enables it via its own @DynamicPropertySource, with an interval set far longer than the test itself runs.

The generalizable lesson: adding a background scheduler to any Spring app changes the risk profile of every test in the suite that boots a full context, not just the tests for the feature the scheduler serves.

BUG 2 A config file that replaced instead of layering — three times
Round 1 — the wrong mental model

To fix Bug 1, a src/test/resources/application.yml was created containing just inventory.reconciliation.enabled: false. Same filename as the real src/main/resources/application.yml. Spring Boot resolves classpath:/application.yml to exactly one file — and Surefire puts test-classes ahead of classes on the classpath — so this new file didn't merge with the main config, it completely replaced it. ddl-auto: update vanished. Every test that touched the database — including ones with nothing to do with reconciliation — started failing with relation "seats" does not exist.

Round 2 — the correct fix

Rename to src/test/resources/application-test.yml and add @ActiveProfiles("test") to the specific test classes that need it. Profile-specific files layer on top of the base config instead of replacing it — this is the actual, documented Spring Boot mechanism for exactly this situation.

Round 3 — the fix didn't actually apply, on disk

Re-running tests still failed with the same "relation does not exist" error, even after deleting the bad file from source. The cause: Maven's incremental test goal copies src/test/resources into target/test-classes, but doesn't delete files from the target that no longer exist in the source. A stale, already-compiled copy of the original shadowing file was still sitting in target/test-classes/application.yml, still winning on the classpath. mvn clean test finally cleared it.

The generalizable lesson: "fixed in source" and "fixed on disk" are different claims. A non-clean incremental build can keep reproducing a bug you've already deleted the cause of.
