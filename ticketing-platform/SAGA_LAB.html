Reader's cheat sheet — if you read only this box

  1. booking-service is a saga orchestrator: given a booking request, it holds seats in inventory-service, charges (stubbed), then confirms. Any step fails → it compensates and marks the booking FAILED. Never oversells, never hangs.
  2. Idempotency-Key header is mandatory on POST /bookings. Same key + same body = same booking returned. Same key + different body = 422. Missing key = 400. The endpoint refuses to be non-idempotent.
  3. State machine: PENDING → SEATS_HELD → PAYMENT_INITIATED → CONFIRMED. Three terminals: CONFIRMED, FAILED, EXPIRED. Invalid transitions blocked in three places (entity method, DB check, @Version).
  4. Booking talks to inventory via Spring RestClient, wrapped in Resilience4j: retry only for transient failures (5xx, timeout), circuit breaker opens when 50% of last 10 calls fail, timeout hard-capped per attempt. Fallback throws, never fakes success.
  5. Every write inside the saga runs in its own TransactionTemplate(REQUIRES_NEW). Same-bean @Transactional would silently bypass the Spring proxy — same trap that produced Day 2's bug #3.
  6. Two Postgres databases (inventory, booking) on ONE Postgres server in local dev — deliberate compromise for this machine. In real AWS these become two separate RDS instances; only env vars change.
  7. Booking does NOT depend on inventory at startup (service_started, not service_healthy). Runtime resilience — not startup ordering — is how microservices stay decoupled.
  8. Every booking retry is idempotent by design: the saga is NEVER re-run for an existing key. Whatever state that booking is in (CONFIRMED, FAILED, in-flight) is authoritative.

The one scenario every section below refers back to

Client taps Book. Network hiccups. They tap again. Meanwhile, booking-service already called inventory-service /hold, and payment is halfway through. Two things must be true no matter which combination of dropped packets and retries happens: exactly one booking exists, and no seat is ever charged for without being confirmed (and vice versa). Every mechanism below exists to make one of those two true.

Why this shape — HLD

Two decisions frame the whole week:

Why a separate booking-service

The booking flow spans three owners (seats, money, notifications) and holds a state machine that lives longer than any single request. Bundling it into inventory-service would tangle two lifetimes — the seat row (permanent) and a booking row (a workflow) — inside one service's transactional boundary. Splitting them lets each fail, scale, and evolve on its own axis.

Why booking owns the coordinator

Someone has to know "we tried to hold, we charged, we're waiting to confirm." That state naturally belongs to the aggregate that started the flow. Making inventory or payment coordinate would push booking-shaped concerns into services that shouldn't care.

Concepts

The theory behind every "why" below.

CONCEPT 1
Two-phase commit is dead — enter the saga

The classic answer to "two databases must agree" is two-phase commit: a coordinator asks every participant "can you commit?", and only when everyone answers yes does it tell them all "then do it." It works. It's also cursed for microservices: every participant blocks its own resources through the whole coordination window, and if the coordinator itself dies mid-round, participants sit locked with no way to safely proceed. In a flash-sale, this is the entire system freezing on one flaky node.

The saga pattern throws away atomicity and buys back eventual consistency: split the transaction into a sequence of local ones, and give every forward step a compensating action that undoes it. A step fails → you don't roll back the world, you run the compensations for what already happened. Nothing is ever locked across a network hop.

Ticketing consequence
Hold seat → charge card → confirm seat. Payment fails? Don't try to un-charge (you never charged the DB — you charged Stripe). Just run /release on the seat. The seat becomes AVAILABLE, the booking becomes FAILED, no user sits blocked on a distributed lock.
CONCEPT 2
Orchestration vs choreography — the branch we picked

Given you've picked a saga, there are exactly two ways to run one.

Orchestration

A central coordinator (here: booking-service) calls each participant in turn and tracks the state. One row on one table knows the whole flow. Debug = read one row + one service's logs.

Choreography

No coordinator. Each service publishes events, other services react. Loose coupling, but the "current state" is an inference across an event stream — great when true, brittle when reasoning at 2am about why a booking is stuck.

We chose orchestration
Three services, complex conditionals (payment OK but confirm fails → refund flow), and a hard requirement that a support agent can read one row and know a booking's fate. Choreography wins later when a fan-out step feeds 4+ independent consumers — the trigger to switch is pre-committed in WEEK2_DESIGN.md §3.
CONCEPT 3
Idempotency-Key — client-supplied, DB-enforced

Every network call can be retried by the client (or a browser, or a mobile carrier). Without protection, a retry of POST /bookings could book the same seat twice — same user, same intent, two bookings, one refund battle.

The pattern: client generates a UUID per attempt and sends it as Idempotency-Key: <uuid>. Server:

  • Same key + same body → return the existing booking (200, not 201).
  • Same key + different body → 422 Unprocessable Entity ("this key already means a different thing").
  • No key → 400 Bad Request. The endpoint refuses to be non-idempotent.
How this project stores it
@Column(name = "idempotency_key", nullable = false, length = 64)
private String idempotencyKey;

// unique index — the DB is the real guarantee
uniqueConstraints = @UniqueConstraint(
    name = "uk_bookings_idempotency_key",
    columnNames = "idempotency_key")

The key lives on the bookings row itself, not a separate idempotency_keys table — the key is the booking's identity from the client's view, so one write does both jobs (record the booking, dedup future retries).

CONCEPT 4
Canonical hash — order-independent request identity

The 422 branch above needs to compare "is this the same body as last time?" But bodies aren't strings — a JSON body with [5,6,7] and one with [7,5,6] mean the same request. Comparing raw bytes would trip a spurious 422 on every legitimate retry that happens to reorder the array.

Solution: canonicalize before hashing
static String canonicalHash(BookingRequest r) {
    List<Long> sortedSeats = r.seatIds().stream().sorted().toList();
    String canonical = r.showId() + "|" + sortedSeats + "|" + r.holderId();
    MessageDigest digest = MessageDigest.getInstance("SHA-256");
    return HexFormat.of().formatHex(digest.digest(canonical.getBytes()));
}

Sorted seats + a fixed field order = one canonical string per logical request. SHA-256 because it's already in every JVM (no new dep) and the collision math is comfortable at billions of bookings.

CONCEPT 5
Why the insert lives in REQUIRES_NEW

Two parallel POST requests with the same fresh key both pass the initial "does this key exist?" lookup, both try to insert. One wins the unique index, the other's insert throws DataIntegrityViolationException. Now — which transaction caught that exception matters.

If both inserts share the caller's transaction
Hibernate marks the session poisoned the moment the constraint violation lands ("don't flush the Session after an exception occurs"). Any follow-up operation in the same tx — even the "re-read the winning row" call — throws with an unrelated-looking AssertionFailure: null id. This is exactly the bug the first version of the race test caught. See B3.
Fix: the insert runs in its own transaction
private TransactionTemplate insertTx() {
    TransactionTemplate tx = new TransactionTemplate(txManager);
    tx.setPropagationBehavior(
        TransactionDefinition.PROPAGATION_REQUIRES_NEW);
    return tx;
}

// caller:
try {
    Booking saved = insertTx().execute(
        status -> insertNew(key, hash, req));
    // ...
} catch (DataIntegrityViolationException race) {
    // insert's tx already rolled back cleanly — safe to re-read
    Booking winner = bookingRepository.findByIdempotencyKey(key)
        .orElseThrow(() -> race);
    // ...
}

The insert's failure is self-contained. The outer method's session was never poisoned. The re-read succeeds. This is the entire mechanism the concurrent-insert test proves — 21st green.

CONCEPT 6
The state machine, enforced at three layers

Six states, one clear happy path, three terminals. The real engineering is that "no EXPIRED → CONFIRMED" isn't a comment in the code — it's enforced three times so no single layer being wrong loses the guarantee.

LayerWhat enforcesBreaks when…
Entity methodmarkConfirmed() reads current status, refuses on a terminal oneApp bug tries the wrong transition
DB check + triggerA raw UPDATE bookings SET status=... on a terminal row is refused by SQLAdmin fix, another service, or a bug in the entity layer
@VersionConcurrent status writes: only the first commits; the second sees OptimisticLockingFailureTwo flows race on the same booking

Day 2 has the entity+@Version layers; the DB trigger arrives with Day 3's state-transition methods.

CONCEPT 7
Compensating actions — every forward step named
Forward stepCompensationIf compensation itself fails
Hold succeeds on some seats, next one 409s/release the successful onesHold TTL is the ultimate safety net (Week 1 already built)
Payment fails after all held/release every held seatSame — TTL + reconciliation sweep
Payment OK but confirm failsRefund (Week 3 wires it) + flag booking for op reviewOp queue — this is a lost booking, not an oversell
Client abandons after heldSweep detects TTL expiry → /releaseNothing to compensate for a no-op
Design rule
Every compensation is idempotent. /release already is (Week 1 guarantee). Retrying a compensation must never make things worse.
CONCEPT 8
Retry + Circuit Breaker + Timeout — three tools, three concerns

One HTTP call to inventory can fail in three genuinely different ways, and each has its own right answer. Bundling them as "just retry harder" is exactly how a small blip becomes a full outage.

FailureWithout protectionRight tool
Brief blip (2s downtime, GC pause)User sees a 502 for a survivable hiccupRetry — a small backoff outlasts it
Persistent outage (5 minutes)Every call blocks a thread; thread pool exhausts; caller crashes tooCircuit Breaker — fail fast, keep threads alive
Slow response (network lag)Caller waits indefinitely; users see hangsTimeout — hard per-attempt bound
Exception hierarchy IS the retry policy
InventoryClientException                 ← IGNORE (never retry — 4xx conflicts)
    └── InventoryTransientException      ← RETRY (5xx, timeout, transport)

retry-exceptions:  [InventoryTransientException]   # explicit whitelist
ignore-exceptions: [InventoryClientException]      # default-safe skip
Why whitelist beats blacklist
Kal a new exception type appears — with a whitelist, its default is "don't retry." With a blacklist, its default would be "do retry," which for a non-idempotent call is the exact accidental-double-charge bug you can't apologize your way out of.
Circuit breaker state machine
       ┌─────────┐   50%+ fails    ┌─────────┐
       │ CLOSED  │────────────────►│  OPEN   │  5s: every call fail-fast
       │(normal) │                 │         │
       └─────────┘                 └────┬────┘
            ▲                           │ 5s elapsed
            │ 3 probes                  ▼
            │ succeed              ┌──────────┐
            │                      │HALF_OPEN │  3 probe calls
            └──────────────────────│          │
             any probe fail →      └──────────┘
             back to OPEN
Fallback must NOT fake success
holdFallback throws InventoryTransientException — booking cannot invent a seat hold. The circuit breaker's job is to fail fast when inventory is genuinely down, not to synthesize a happy path that leads to a silent oversell. The saga's existing FAILED-plus-compensate branch is where the failure lands cleanly.
CONCEPT 9
Compose networking — hostnames are service names, not localhost

Inside a docker-compose network, each service has its own DNS name equal to its services: key. Booking calls inventory as http://inventory-service:8081, not http://localhost:8081.

The predictable trap
localhost inside booking's container loops back to booking's own container. Nothing there listens on 8081 → connection refused. Symptom: mysterious "inventory always down" only inside compose, works fine from the host.
One-Postgres-two-databases — a deliberate local-dev compromise
postgres/
  ├── inventory   (owned by inventory_user)
  └── booking     (owned by booking_user)
"Database-per-service" 's real invariant is no cross-service JOINs, not "one container per DB." Sharing one Postgres server locally saves memory on this fragile-Docker machine; in real AWS these become two separate RDS instances with zero code change (only env vars).
CONCEPT 10
Startup coupling — the trap you added by "being safe"

Instinct: booking-service depends_on: inventory-service: condition: service_healthy. Looks correct. Wait for inventory before starting booking.

Why it's wrong for microservices
It couples the two services' startup ordering. If inventory takes 30s to come up, booking sits idle for 30s — its container health is dictated by a peer's. Now imagine 6 services in a chain: startup becomes a serialized parade, and any one service's slow restart blocks the world.
The right posture: service_started + runtime resilience
Booking says "I'm up as long as MY dependencies (Postgres) are healthy." If inventory is momentarily unreachable during booking's boot, that's exactly what Resilience4j exists to absorb. The retry + circuit breaker on outgoing calls means "inventory not ready yet" behaves the same as any other transient failure — bounded, tracked, fallible per-request, not fatal per-service.

DAY 3
Saga wiring — PENDING → CONFIRMED (or clean FAILED)
new: InventoryClient, InventoryClientException, PaymentStub, BookingSagaService, BookingProperties · updated: Booking, BookingService, GlobalExceptionHandler, application.yml · new tests: BookingSagaServiceTest (5)
What happens now on a fresh POST /bookings
1. BookingService.create() inserts PENDING row (own tx, commits)
2. BookingSagaService.runSaga():
     for each seat: inventoryClient.hold(...)   → record hold_token
     → mark SEATS_HELD
   → paymentStub.charge(...)   → payment_ref
     → mark PAYMENT_INITIATED
   → for each seat: inventoryClient.confirm(...)
     → mark CONFIRMED (final)
3. Response 201 with the full CONFIRMED booking

The saga runs OUTSIDE the initial insert's transaction on purpose. If it ran inside, a crash after inventory /hold but before the tx commits would leave a held seat with no booking row to compensate against — an orphaned held seat, silently. Committing PENDING first means every downstream side-effect has a durable audit anchor.

On failure — same endpoint, different exit
  • Hold fails on seat 1 → no compensation needed → mark FAILED → 502 Bad Gateway with bookingId in the body.
  • Hold succeeds on seat 1, fails on seat 2 → release seat 1 → mark FAILED → 502. Bridge row for seat 1 gets a released_at stamp; seat 2's stays null (never held).
  • All holds OK, payment fails → release every held seat → mark FAILED → 502.
  • Release itself fails during compensation → log, swallow, mark FAILED anyway. Inventory's own hold TTL + reconciliation sweep (Week 1) is the ultimate safety net.
Idempotent retry never re-runs the saga
Same key + same body → return the current stored state (CONFIRMED, FAILED, or still-flowing). Re-running would double-charge or double-hold. This is why idempotency is enforced before any side-effect fires.

DAY 3.5
Resilience4j on the outgoing calls
new: InventoryTransientException, InventoryRestClientConfig · updated: InventoryClient (@Retry + @CircuitBreaker + fallbacks), pom.xml (resilience4j-spring-boot3), application.yml (retry + CB config)

Scope: transient failures against inventory now retry with exponential backoff; persistent failure opens a circuit breaker that fails subsequent calls fast; timeout was already on the RestClient itself. Together they turn "inventory is flaky" from a caller-facing crash into a caller-facing 502 with a compensated booking row — exactly what the saga was designed to handle.

The one design decision that made it clean
Split the exception into InventoryClientException (base) and InventoryTransientException (retryable subclass). Config points Retry at the subclass, tells it to ignore the base — so the saga's existing catch (InventoryClientException) still catches everything, and Retry knows which is safe to try again. See Concept 8.
Config, in one glance (application.yml)
resilience4j.retry.instances.inventory:
  max-attempts: 3
  wait-duration: 200ms
  exponential-backoff-multiplier: 2      # 200ms → 400ms → 800ms
  retry-exceptions:  [ InventoryTransientException ]
  ignore-exceptions: [ InventoryClientException ]

resilience4j.circuitbreaker.instances.inventory:
  sliding-window-size: 10
  failure-rate-threshold: 50             # 50%+ fails → OPEN
  wait-duration-in-open-state: 5s
  permitted-number-of-calls-in-half-open-state: 3
  automatic-transition-from-open-to-half-open-enabled: true
  record-exceptions: [ InventoryTransientException ]
  ignore-exceptions: [ InventoryClientException ]  # 4xx is NOT unhealthy

DAY 5
Failure experiments — designed on paper

Four experiments, each one designed BEFORE we run them so the expected outcome is a real prediction (interview-answerable) not a post-hoc rationalization:

ExperimentHow to runWhat it must prove
1. Inventory killed mid-saga docker compose stop inventory-service, then POST /bookings Resilience4j retry fires 3×, CB opens after N fails, booking cleanly FAILED with 502. No hung threads, no cascading crash of booking-service itself.
2. Payment fails Restart booking with BOOKING_PAYMENT_SIMULATE_FAILURE=true, POST /bookings Hold succeeds, payment throws, compensating release fires per seat, seats return to AVAILABLE, booking marked FAILED. Bridge rows have released_at stamps.
3. Response lost on confirm Kill booking mid-flight (or drop the response with a proxy), client re-posts with same Idempotency-Key Same key + same body → SAME bookingId returned. No double-charge, no double-hold. The idempotency guarantee from Day 2 now enforced across a distributed failure scenario.
4. Two parallel bookings, same seat Two curls in parallel to POST /bookings with different keys but overlapping seatIds Exactly one booking CONFIRMED, exactly one FAILED with 502. The 409 from inventory is non-transient (see Concept 8), so no retry storm — clean fail on the losing side. This is Week 1's oversell guarantee, now enforced through a service boundary.

What ties them together: every experiment either exercises a compensation path (1, 2) or a correctness invariant (3, 4). Failure experiments only earn their cost when the prediction is written down first — otherwise it's just "let's break stuff and see." The whole point of a saga is the rollback story, so if these four don't produce their expected outcomes, the saga is broken, not the tests.

BUG 4
Postgres init script silently skipped on non-fresh volume
Symptom (live-caught 2026-09-18 during Day 4 first-boot)
Both containers came up healthy. But booking-service would have failed at boot with "database 'booking' does not exist" — because docker exec ... psql -c '\l' showed only inventory, postgres, template0/1. No booking DB, no booking_user.
Root cause + fix
The Postgres image's /docker-entrypoint-initdb.d runs its scripts exactly once — on the FIRST container start against a FRESH volume. Any subsequent restart (including docker compose up against an existing pgdata) skips the init entirely. Because I'd tested inventory-service before adding the booking init, the volume already had data → init never ran. Fixes: docker compose down -v (nuke volume) then up — heavyweight; OR manually run the init SQL against the running container: 
docker exec ticketing-platform-postgres-1 psql -U inventory_user -d postgres \
  -c "CREATE USER booking_user WITH PASSWORD 'booking_pass';"
docker exec ticketing-platform-postgres-1 psql -U inventory_user -d postgres \
  -c "CREATE DATABASE booking OWNER booking_user;"

Lesson worth keeping: anything that says "runs on first start" in Docker land really means "runs when the volume is empty, silently skipped otherwise." Prod-safe alternative is Flyway/Liquibase inside the app itself — schema migrations that run every startup, regardless of volume state. Week-2 uses ddl-auto: update which is fine for the entity DDL, but the CREATE DATABASE step needs a Flyway-equivalent for real deployments.

BUG 5
The one that made retry NEVER fire — ignore-exceptions parent trap
Symptom (live-caught during Day 4 Experiment 4)
Killed inventory-service, hit POST /bookings. Expected: retry 3× with exponential backoff, total elapsed ~1500ms, log shows 3 transport-error lines. Got: elapsed 194ms, exactly ONE transport-error line in the log. Retry was silently doing nothing.
Root cause
My original config: 
retry-exceptions:  [ InventoryTransientException ]
ignore-exceptions: [ InventoryClientException ]   # ← THIS was the trap
InventoryTransientException extends InventoryClientException. Resilience4j's ignoreExceptions matching uses isInstance — so the PARENT class in the ignore list also matches the subclass. The retryable subclass got matched by both the retry whitelist AND the ignore blacklist, and ignore wins. Result: no retry ever fires. Absolute silent failure.
Fix — remove ignore-exceptions
When retry-exceptions is set explicitly, Resilience4j only retries those (and their subclasses); everything else is automatically not retried. ignore-exceptions is redundant here, and — as this bug proves — actively dangerous when it names a parent of a retry-exception type. 
# WRONG (what I had):
retry-exceptions:  [ InventoryTransientException ]
ignore-exceptions: [ InventoryClientException ]

# RIGHT:
retry-exceptions:  [ InventoryTransientException ]
# no ignore-exceptions — whitelist alone is sufficient

Live-verified after fix: same experiment → elapsed 1533ms, three transport-error lines with the same correlation-id in the log. Retry firing correctly.

Lesson worth keeping: exception hierarchy meets whitelist/blacklist matching in surprising ways — always test both fire AND no-fire paths against the real config, not just the config's stated intent. If I hadn't lived-verified this, we'd have shipped a "retry" that never retried.

BUG 6
CB opened correctly, but Retry kept retrying the CB-open fallback
Symptom (live-caught immediately after fixing B5, Day 4)
Fired 7 rapid requests with inventory down. CB opened correctly around request 3–4 (log shows inventory_circuit_open lines). But elapsed times stayed ~650ms per request — never dropped to the ~10ms "fast-fail" the CB is supposed to provide.
Root cause
Default aspect ordering in Resilience4j is: Retry OUTER, CB INNER. Each Retry attempt goes through the CB. When CB is open, the CB fallback method runs. My fallback threw InventoryTransientException — which is IN retry-exceptions. So Retry saw the fallback's exception, matched it as retryable, and retried 3× more. Each of those retries also hit CB fallback, also threw transient, also retried. Fast-fail was cancelled by wasted retry rounds.
Fix — fallback throws the NON-transient base type
// WRONG:
throw new InventoryTransientException(0, "circuit open for hold", open);

// RIGHT:
throw new InventoryClientException(0, "circuit open for hold", open);

Base InventoryClientException is NOT in retry-exceptions → Retry skips it → CB-open really does fast-fail. The saga still catches the base exception and marks FAILED — behavior unchanged for the caller.

Live verified after fix: attempt 1 = 1578ms (retry against real dead inventory), attempt 2 = 641ms (fewer retries as CB starts opening), attempts 3+ = ~200ms consistent (CB open, single fallback call per request, no retry storm). Exactly the shape the design promised on paper.

Lesson worth keeping: when Retry wraps CB (the Spring Boot Resilience4j default), the fallback's exception shape drives the outer behavior. A fallback throwing a retryable exception silently defeats the CB's fast-fail promise. Either change the exception shape (this fix) or reverse the aspect ordering.

Bug museum — three real ones from Day 2

BUG 1
@Override signature drift across Spring versions
Symptom
Fresh compile: method does not override or implement a method from a supertype on handleMissingRequestHeader.
Root cause + fix
The ResponseEntityExceptionHandler base has quietly shifted the signature of that method between Spring 6 minor versions — the @Override broke against 6.2.x. Fix: don't override the base method at all. Handle it via a direct @ExceptionHandler(MissingRequestHeaderException.class) — same behavior, no base-class coupling. Lesson: overriding a framework's protected method means the framework can change its shape under you; a top-level @ExceptionHandler is the more stable seam.
BUG 2
@MockBean import path — copy-paste-guessed wrong
Symptom
package org.springframework.boot.test.mockito does not exist. Cannot find symbol MockBean.
Root cause + fix
Correct package is org.springframework.boot.test.mock.mockito.MockBean. The subtle nesting — mock.mockito, not mockito — is easy to fumble writing from memory. Cross-checked inventory-service's own tests to be sure. Lesson: when reusing a pattern from a working sibling module, copy the exact import, don't retype it.
BUG 3
The Day-2 bug: Hibernate refuses to flush after a constraint violation
Symptom
The concurrent-insert race test — the one that specifically proves idempotency under real threads — failed with a confusing error: org.hibernate.AssertionFailure: null id in com.ticketing.booking.entity.Booking entry (don't flush the Session after an exception occurs). Everything else was green.
Root cause
Original code kept everything in one @Transactional method: check → insert → catch DataIntegrityViolationException → re-read. But Hibernate's session is stateful. The moment the INSERT fails on the unique index, the session is poisoned — any subsequent operation in the same transaction (including the follow-up "re-read the winning row") triggers that AssertionFailure, because internal entity bookkeeping is now inconsistent. Hibernate is telling you: "don't do more work in this transaction, roll it back and start fresh."
Fix
Move the INSERT into its own transaction via TransactionTemplate with PROPAGATION_REQUIRES_NEW. When the constraint violation lands, that transaction rolls back cleanly and independently. The outer flow's session was never poisoned, so the re-read runs against a healthy context. 
// before: everything in one @Transactional method → race test fails
// after:
try {
    Booking saved = insertTx().execute(
        status -> insertNew(key, hash, req));      // OWN tx
    return new BookingCreationResult(toResponse(saved), true);
} catch (DataIntegrityViolationException race) {
    // insertTx already rolled back — safe to re-read
    Booking winner = bookingRepository.findByIdempotencyKey(key)
        .orElseThrow(() -> race);
    return matchOrThrow(winner, hash, key, false, "race_lost");
}

Lesson worth keeping: "catch and continue" across a JPA transaction only works if you catch the failure outside the transaction where it happened. When the failure is a constraint violation on flush, that's non-negotiable — the session state after that flush is not something you're allowed to keep using.

Decision log — where we picked A over B and why

The decisions worth remembering. In each case there's a real B that would have looked reasonable; here's why we didn't pick it.

Orchestration over choreography

Why not choreography (event-driven, no coordinator): three services, complex conditional logic (payment OK but confirm fails → refund), hard requirement that a support agent read ONE row to know a booking's fate. Choreography makes state an inference across an event stream — great when true, brittle at 2am. Revisit trigger pre-committed: switch parts to choreography when a step naturally serves 4+ independent consumers.

DECISION
Idempotency-Key on the row, not a separate table

Why not a separate idempotency_keys table: the key IS the booking's client-side identity, so its dedup evidence belongs with it. One INSERT with a UNIQUE index does both jobs (record + dedup). A separate table is one more write, one more thing that can race with the booking insert.

DECISION
Exception hierarchy for retry policy, not a predicate class

Why not a Java Predicate<Throwable> in config: a predicate hides its intent inside code. Class hierarchy expresses "these are retryable, these are not" declaratively. New exception subtype gets the correct default from its parent, no config drift. And the saga's own catch (InventoryClientException) still handles both without knowing.

DECISION
Fallback throws, no graceful degradation

Why not return a "circuit-open" sentinel HoldResponse: booking-service cannot invent a seat hold. Any sentinel that flows into the saga's happy path is a silent oversell waiting to happen. Fail-fast reveals the truth immediately, and the saga's existing FAILED-plus-compensate path handles it correctly.

DECISION
Copy GlobalExceptionHandler across services, not extract a shared lib

Why not ticketing-platform-common lib: a shared lib couples deploy cycles for a class of change (add a mapping, tweak a message) that would otherwise be independent per service. Duplication is cheap. Coupling is expensive. Same reason inventory-service and booking-service each have their own CorrelationIdFilter.

DECISION
TransactionTemplate(REQUIRES_NEW) over @Transactional on private methods

Why not just annotate helper methods: same-bean @Transactional is invisibly bypassed by Spring's proxy on internal calls — the transaction quietly doesn't exist. TransactionTemplate is explicit; the transaction boundary is visible where it lives. Same reason Day 2 fixed its bug by moving the insert into a template.

DECISION
Payment as an in-service stub for now, not a separate service

Why not stand up a payment-service container today: Week 3's whole scope is "split payment into its own service and add strategy for UPI/Card." Anticipating that today = double work. The stub sits behind a class boundary (PaymentStub) so the split is a swap, not a rewrite.

DECISION
Learning-first, JUnits at Week 2 end pass

Why not test-driven at every step: Day 3.5 is a genuinely new learning surface (Resilience4j semantics + Spring AOP interaction + MockRestServiceServer wiring). Chasing a green bar can crowd out the actual understanding. Discipline for this week: implement + mentally walk through + document the reasoning; write proper JUnits in one clean pass over the finished shape.
