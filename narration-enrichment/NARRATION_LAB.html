DAY 2 Breaking the naive approach on purpose
day2_naive_json.py
Goal

Ask for JSON with a deliberately casual prompt — no "ONLY JSON", no field types spelled out — and parse the raw text with plain json.loads(). No safety net.

Prompt used (word for word)
Look at this bank transaction narration and tell me the
merchant, the category, the transaction type, and how confident you are.

Narration: {narration}

Give me this as JSON.
Real output — three narrations, three different failures
NarrationWhat came backFailure
...SWIGGY...```json {...} ```fence
...SALARY..."confidence": "High"wrong type
...AMAZON..."confidence": {"score":.98,"level":"Very High"}wrong shape
What actually crashed

json.loads() failed on all three — every response was wrapped in a markdown fence, so parsing died on the backtick before it ever reached the "High" string or the nested object. Data that was arguably still usable never even got read.

The twist

A more careful prompt (Day 1's — "Return ONLY a JSON object with exactly these fields...") had produced clean output on these same narrations. Better wording helped — but it's not a guarantee, and this project needed one.

DAY 3 Forcing the shape instead of hoping for it
models.py · day3_structured_output.py
The schema (models.py)
class TransactionEnrichment(BaseModel):
    merchant: str
    category: Literal["food_delivery","shopping","salary","transfer","other"]
    transaction_type: str
    confidence: float = Field(..., ge=0.0, le=1.0)
Same prompt, same narrations as Day 2 — new call site
client = instructor.from_genai(raw_client, model=MODEL)
result = client.create(
    response_model=TransactionEnrichment,

    max_retries=3,
)
Real output — all three, this time
type: TransactionEnrichment ← a real object, not a dict confidence: 0.95 (float)

Not luck, and not a smarter prompt — Gemini's native function-calling (Instructor's default Mode.TOOLS) makes the model call a function shaped exactly like the schema. A string can't land in a float-typed argument slot; the fence and the nested object aren't things a function call can even produce.

Go deeper — the reask mechanism, from Instructor's own source

Verified in instructor/v2/providers/genai/handlers.py. On a validation failure, reask_genai_tools() builds the next attempt's conversation:

error_msg = f"Validation Error found:\n{exception}\nRecall the function correctly, fix the errors"
function_response_part = types.Part.from_function_response(
    name=function_call.name,
    response={"error": error_msg},
)

from_function_response(...) is normally how a real tool's real result gets reported back to Gemini after it calls one. Instructor reuses that exact channel to report a validation failure instead — Gemini has seen this shape of turn thousands of times in training as "a tool call didn't work, try again," and reacts to it far more reliably than a bolted-on text message would get.

In retry.py, only four exception types are treated as retryable at all: ValidationError, json.JSONDecodeError, AsyncValidationError, ResponseParsingError. Anything else — a network timeout, an auth failure — is not retried; it propagates immediately. That's a deliberate split: a shape problem is worth asking the model to fix, an infrastructure problem is not something asking the model again will ever solve.

max_retries=3 becomes stop_after_attempt(4) — one original attempt plus three reasks, maximum. Every attempt is a full, billed API call.

Go deeper — why patch("...main.enrich_narration"), not "...service.enrich_narration"

main.py runs from narration_enrichment.service import enrich_narration. That import binds a second name to the same function object — inside main's own namespace. When the route handler runs, it looks up enrich_narration in its own module's namespace, not back in service.

Patch service.enrich_narration and main's copy of the name is untouched — the real function still runs. The patch has to target the name where it's looked up at call time, which is wherever it was imported to, not wherever it was originally defined.

Week 2

Measure it, scale it, survive its own outages

Week 1 proved the pipeline could produce correct, typed output once. Week 2 asks three harder questions: how do you know it's still correct after you change something, what happens when there are 50 narrations instead of 1, and what happens when the provider itself has a bad minute.

Bug found — free tier is much more limited than it looks

Running all 12 narrations back-to-back hit a real 429 almost immediately:

429 RESOURCE_EXHAUSTED Quota exceeded for metric: generate_content_free_tier_requests quotaId: GenerateRequestsPerMinutePerProjectPerModel-FreeTier, quotaValue: '5'

Paced calls 13s apart to stay under 5/minute — then hit a second, unrelated cap on the very next run:

quotaId: GenerateRequestsPerDayPerProjectPerModel-FreeTier, quotaValue: '20' No amount of pacing fixes this one — it resets once a day, period.
Bug found — the 10s timeout was too tight

Of 12 calls that got past the rate limit, 4 (33%) failed with 504 DEADLINE_EXCEEDED at the original 10s timeout. Raised to 20s in config.py based on this measurement — not a guess.

Summary output (the honest version — completion rate separate from accuracy)
calls completed 8/12 call failure rate 33% (reliability, not correctness — timeouts/quota/outages) accuracy: merchant 100% (of calls that completed) accuracy: category 100% (of calls that completed) accuracy: all fields 100% (of calls that completed)

The naive read of "67% correct" would have been wrong to act on — the model was 100% correct whenever it actually got to respond. The real problem this eval run surfaced was reliability, not prompt quality.

PHASE 2 Batch processing & persistence
db.py · schemas.py · main.py
Goal

A real bank statement has dozens of lines, not one — and Week 1's pipeline forgot every result the moment it answered. Added POST /enrich/batch (up to 50 at once, each isolated) and a SQLite-backed EnrichmentRecord table so results outlive the request.

Per-item isolation (the actual batch-processing lesson)
for index, narration in enumerate(request.narrations):
    try:
        result = _enrich_and_persist(narration, db)
        results.append(BatchItemResult(index=index, success=True, ...))
    except Exception as exc:
        results.append(BatchItemResult(index=index, success=False, error=type(exc).__name__))
Bug found — SQLite ":memory:" + connection pooling

First test run against an in-memory test database failed immediately:

sqlite3.OperationalError: no such table: enrichment_records

SQLite's :memory: database lives inside a single connection — SQLAlchemy's default pool handed create_all() one connection and the test's query a different one, which had never seen the table. Fixed with poolclass=StaticPool, forcing every checkout through the same connection.

Bug found — the volume mount was missing

The original docker-compose.yml had no volume. The SQLite file would have lived inside the container's writable layer and vanished on every docker compose down — a real, easy-to-miss data-loss bug for anyone's first Docker+DB setup.

$ docker compose exec narration-enrichment uv run python -c "...save_enrichment(...)..." saved id 1 $ docker compose down && docker compose up -d $ curl http://localhost:8000/enrichments [{"id":1,"merchant":"Docker Volume Test",...}] ← survived the restart
PHASE 3 Production reliability — retry-with-backoff
service.py · tests/test_service_retry.py
Goal

Phase 1 hit real 429/503/504 errors live. Instructor's own retry (Day 3) only retries a bad shape — a failed call propagates immediately. This phase adds a second, separate retry layer for exactly that.

Code
_TRANSIENT_CODES = {429, 503, 504}  # found live in Phase 1 — not a guess

def _is_transient_provider_error(exc):
    return isinstance(exc, APIError) and exc.code in _TRANSIENT_CODES

@retry(retry=retry_if_exception(_is_transient_provider_error),
       stop=stop_after_attempt(3), wait=wait_exponential(multiplier=1, min=1, max=10),
       reraise=True)
def _call_llm(narration): ...
Two retry layers, two different jobs
LayerRetries whatBecause
Instructor's max_retries (Day 3)bad shape (ValidationError)the model can fix its own mistake if shown the error
tenacity's @retry (Phase 3, new)failed call (429/503/504)the provider was briefly unavailable — the SAME request tried again may just work

A 400 or 404 is deliberately not in _TRANSIENT_CODES — those fail identically every time, so retrying just makes the caller wait 3x longer for the same answer. main.py got a fourth except APIError block too, mapped to 503 (not a generic 500) — meaning even the exhausted-retry case tells the caller "try again," not "something's broken."

Week 3

A live run catches what 30 passing tests missed

Day 1 of Week 3 was meant to be a quick re-confirmation: quota resets overnight, run the eval once more for a clean baseline. It surfaced a real bug in Phase 3's retry logic instead — one that had shipped, passed code review, passed 9 tests, and never once fired in production.

WEEK 3 · D1 The retry logic that never ran
service.py · main.py · tests/test_service_retry.py · tests/test_api.py
What a clean re-run looked like
calls completed 11/12 call failure rate 8% accuracy: all fields 100% (of calls that completed)

Good news on the surface — but the one failure's error string was InstructorRetryException: 504 DEADLINE_EXCEEDED..., not the raw APIError the Phase 3 retry code was written to catch.

The bug — mocked at the wrong boundary

_is_transient_provider_error checked isinstance(exc, APIError). Instructor's own internal retry loop catches every exception from the real API call and re-raises it as InstructorRetryException(...) from original_error — .create() never raises a bare APIError. Confirmed by mocking one layer deeper than the tests did:

with patch.object(_raw_client.models, 'generate_content', side_effect=err): _call_llm('test') Exception seen by caller: InstructorRetryException Is APIError? False __cause__ type: APIError · code: 504

The Week 2 tests had mocked _client.create directly — one layer higher — which raises whatever you tell it to, unwrapped. That mock was internally consistent and completely unlike reality.

The fix
def _is_transient_provider_error(exc):
    if isinstance(exc, APIError) and exc.code in _TRANSIENT_CODES:
        return True
    cause = exc.__cause__
    return isinstance(cause, APIError) and cause.code in _TRANSIENT_CODES
A second bug this exposed, in main.py

An exhausted transient error and a genuine shape failure both raise InstructorRetryException — so a real, retried-3x, still-failing 503 was landing in the same branch as "the model gave bad output," and being reported to the caller as 422 instead of 503. Fixed by checking exc.__cause__ inside that one except block before deciding the status code.

tests/test_service_retry.py::test_transient_codes_are_recognized_via_the_wrapped_exception PASSED tests/test_api.py::test_enrich_returns_503_when_a_transient_provider_error_exhausts_retries PASSED 30 passed — this time against the exact exception shape confirmed live

Nothing here needed a second LLM provider, a bigger retry library, or more code — the fix is two lines. The lesson is the mocking boundary: a mock one layer off from reality can pass every test in the file and still test nothing real.

5 Dockerfile Recipe for building the image

Read top to bottom — each line either sets up the environment or copies something in. Order matters here more than in normal code.

LineWhat it does
FROM ghcr.io/astral-sh/uv:...Start from an image that already has Python 3.11 and uv pre-installed — no separate install step needed.
WORKDIR /appEvery following instruction runs inside /app from here on.
COPY pyproject.toml uv.lock ./Copy only the dependency manifest first — not the code yet.
RUN uv sync --frozen --no-install-project --no-devInstall exactly the locked dependency versions. --no-dev skips pytest — this is a runtime image. --no-install-project skips our own code — it isn't copied in yet.
COPY src ./srcNow bring in the actual application code.
RUN uv sync --frozen --no-devRun again — this time it also installs our own package, now that the code exists.
EXPOSE 8000Documentation only — says "this container listens on 8000." The real port mapping happens in compose.

Why two COPY+RUN pairs instead of one: Docker caches each step. Dependencies rarely change; code changes constantly. Splitting them means an ordinary code edit skips the slow dependency-install step entirely — Docker reuses the cached layer from before.
