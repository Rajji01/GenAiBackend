LLM concepts

The theory behind every day below

Seven ideas, each explained twice: what's actually going on inside an LLM API in general, and exactly where that theory shows up as a real finding, bug, or design choice in this project — not as a separate lecture, as the reason the code looks the way it does.

CONCEPT 1 Next-token generation — why "just ask for JSON" is fragile
The theory

An LLM is, mechanically, a next-token predictor: given the tokens so far, it produces a probability distribution over what token comes next, samples one, and repeats. It has no built-in notion of "a JSON document" as a structural contract — it's producing a plausible continuation of the conversation, token by token. When a prompt says "respond with JSON," the model is *statistically inclined* to comply because of how it was trained (instruction-tuning, RLHF), not because anything mechanically forces the output into a valid, parseable shape.

Exactly this, reproduced live — Day 2

Three different, real failures came from this one gap between "usually complies" and "mechanically guaranteed": a response wrapped in a ```json markdown fence (the model treating its answer as a code block, a very common training-data pattern), "confidence": "High" (a string where a float was asked for — the model paraphrased the *concept* correctly, not the *type*), and a fully nested object where a scalar was expected. None of these are "the model being bad" — they're next-token generation doing exactly what it does, with nothing to stop a plausible-but-wrong shape from being just as likely as the right one.

CONCEPT 2 Tokens, context windows, and where "thinking" fits in the budget
The theory

Models don't process text as characters or whole words — they process tokens, subword chunks a tokenizer maps text into. Every model has a maximum context window (the total tokens it can hold in play at once — input plus output) and often a separate hard cap specifically on output length (max_output_tokens). Reasoning-capable models like gemini-3.6-flash can generate internal "thinking" tokens before producing the visible answer — and on many providers, those thinking tokens are drawn from the same output budget as the answer itself, not a separate allowance.

Day 1, live: max_output_tokens set too low -> model spent its whole budget "thinking" -> visible answer silently truncated, no error raised

This wasn't in any doc read beforehand — it was found by making one real call, inspecting the actual token usage in the response, and noticing the visible text was cut short with no exception thrown. A model failing silently, not loudly, is the whole reason this was worth checking for real instead of assuming a "reasonable" token limit would just work.

CONCEPT 3 Function/tool calling — structure enforced by the API, not the prompt
The theory

Function calling (also called tool calling) is a native capability most modern LLM APIs expose, separate from plain chat completion. The caller supplies a schema — field names, types, which are required — describing a "function" the model can call. The provider constrains generation so the model's output for that turn is a structured arguments payload matching the schema, returned as its own distinct object in the API response, not as free text you then have to parse yourself. This is enforced at the decoding/API level, which is why it's categorically more reliable than a prompt that just asks nicely for JSON (Concept 1).

Day 2 — prompting for JSON

A casual prompt, the model's raw text response parsed with json.loads(). All three of Concept 1's failures came from exactly this path.

Day 3 — Instructor's Mode.TOOLS

response_model=TransactionEnrichment becomes the function schema Gemini is constrained against. Same three narrations, same model — all three came back clean, typed, and validated.

Why this is the primary defense, and max_retries is only a safety net

Mode.TOOLS is what makes a correct shape likely by construction, not just likely by luck. The retry on top of it exists for the rarer case where even a schema-constrained call still comes back with something the Pydantic model rejects (an out-of-range confidence, an unrecognized category) — a second line of defense, not the first.

CONCEPT 4 Embeddings & cosine similarity — meaning as geometry
The theory

An embedding model maps a piece of text to a fixed-length vector of floats, trained so that texts with similar meaning land at vectors pointing in similar directions — regardless of exact wording. Cosine similarity measures exactly that: the cosine of the angle between two vectors, ranging from -1 (opposite meaning) to 1 (identical meaning), deliberately ignoring vector length so it compares orientation, not magnitude. This is what turns "search by meaning" into ordinary arithmetic: dot product divided by the product of norms.

def cosine_similarity(a: list[float], b: list[float]) -> float:
    dot = sum(x * y for x, y in zip(a, b))
    norm_a = math.sqrt(sum(x * x for x in a))
    norm_b = math.sqrt(sum(y * y for y in b))
    return dot / (norm_a * norm_b) if norm_a and norm_b else 0.0
Asymmetric retrieval — a real detail, not a footnote

Gemini's embedding model treats "text being stored for later search" (task_type=RETRIEVAL_DOCUMENT) and "text doing the searching" (task_type=RETRIEVAL_QUERY) as different jobs internally, optimizing each differently. Using the same task_type for both doesn't error — it just quietly produces worse similarity scores. This is exactly the kind of thing you only catch by reading the actual API semantics, not by guessing that "an embedding is an embedding."

CONCEPT 5 RAG — grounding a frozen model in data it never trained on
The theory

An LLM's weights are frozen at training time — it knows nothing about data created after that cutoff, or data specific to one deployment (your own users' past decisions, your own documents). Retrieval-Augmented Generation solves this without touching the model at all: at request time, relevant external context is retrieved (via embeddings + similarity search, Concept 4) and folded directly into the prompt as extra information the model can use for this one call. The model isn't retrained or fine-tuned — it's handed the right context, on demand, right when it needs it.

Live proof, Week 3: seeded "UBER TRIP PAYMENT" -> category="transfer" Query: a fresh, near-identical "UBER TRIP PAYMENT" narration WITHOUT retrieved context: other (matches the original, RAG-less finding) WITH retrieved context: transfer (follows the retrieved past decision)

Same model, same weights, same prompt template — the only variable was whether retrieved context was present. This is the theory made concrete: nothing about the model changed, only what it was shown.

CONCEPT 6 Provider quotas — usually more than one axis at once
The theory

LLM APIs commonly enforce several independent quota axes simultaneously — requests-per-minute (protects against bursts), tokens-per-minute (protects against a few huge requests instead of many small ones), and requests-per-day (protects overall capacity planning). Hitting any one of them returns a 429, and different axes reset on completely different clocks — a per-minute cap clears in seconds, a per-day cap doesn't clear until the next day regardless of how patiently you wait and retry.

Both axes, found live — Phase 1

Running the Week 2 eval unpaced surfaced two separate 429s with different quotaIds: a 5 requests/minute cap, and a 20 requests/day cap. Nothing in the docs was consulted first — this came from reading the actual error payload of a real 429.

This is precisely why Week 4's rate limiter tracks two independent sliding windows rather than one — a single "requests per minute" counter would have been solving only half of a two-part real constraint.

CONCEPT 7 Retry strategy — a failed call and a wrong shape are different problems
The theory

Not every LLM failure calls for the same fix. A transient failure (429 rate-limited, 503 overloaded, 504 timed out) means the exact same request would likely succeed if sent again after a short wait — classic exponential-backoff territory, and retrying doesn't need to know anything about what was asked. A shape/validation failure (the model's output doesn't match the required structure) is a completely different problem: retrying the identical request would likely fail identically, since nothing about the situation changed. What actually helps is a reask — feeding the model back its own bad output plus the specific validation error, so the next attempt has new information to correct against.

Instructor's own retry (max_retries)

A reask loop for shape failures — the model sees what it got wrong last time, not a blind repeat.

service.py's tenacity retry

Exponential backoff for transient provider errors (429/503/504) — a completely separate mechanism, deliberately not merged with the one above.

Week 3, Day 1 — confusing which layer actually fired

Instructor wraps every underlying failure — including an already-exhausted transient error — in the same InstructorRetryException type it uses for a genuine shape failure. Treating them as the same thing meant an exhausted 503 (the provider being down, Concept 6/7's transient case) was being reported to callers as a 422 ("your input was bad," Concept 1's shape case) — two different problems wearing the same exception type. The fix was inspecting exc.__cause__ to tell them apart before deciding the response.

Not luck, and not a smarter prompt — Gemini's native function-calling (Instructor's default Mode.TOOLS) makes the model call a function shaped exactly like the schema. A string can't land in a float-typed argument slot; the fence and the nested object aren't things a function call can even produce.

Go deeper — the reask mechanism, from Instructor's own source

Verified in instructor/v2/providers/genai/handlers.py. On a validation failure, reask_genai_tools() builds the next attempt's conversation:

error_msg = f"Validation Error found:\n{exception}\nRecall the function correctly, fix the errors"
function_response_part = types.Part.from_function_response(
    name=function_call.name,
    response={"error": error_msg},
)

from_function_response(...) is normally how a real tool's real result gets reported back to Gemini after it calls one. Instructor reuses that exact channel to report a validation failure instead — Gemini has seen this shape of turn thousands of times in training as "a tool call didn't work, try again," and reacts to it far more reliably than a bolted-on text message would get.

In retry.py, only four exception types are treated as retryable at all: ValidationError, json.JSONDecodeError, AsyncValidationError, ResponseParsingError. Anything else — a network timeout, an auth failure — is not retried; it propagates immediately. That's a deliberate split: a shape problem is worth asking the model to fix, an infrastructure problem is not something asking the model again will ever solve.

max_retries=3 becomes stop_after_attempt(4) — one original attempt plus three reasks, maximum. Every attempt is a full, billed API call.

Bug found — SQLite ":memory:" + connection pooling

First test run against an in-memory test database failed immediately:

SQLite's :memory: database lives inside a single connection — SQLAlchemy's default pool handed create_all() one connection and the test's query a different one, which had never seen the table. Fixed with poolclass=StaticPool, forcing every checkout through the same connection.

Week 3

A live run catches what 30 passing tests missed

Day 1 of Week 3 was meant to be a quick re-confirmation: quota resets overnight, run the eval once more for a clean baseline. It surfaced a real bug in Phase 3's retry logic instead — one that had shipped, passed code review, passed 9 tests, and never once fired in production.

WEEK 3 · D1 The retry logic that never ran
service.py · main.py · tests/test_service_retry.py · tests/test_api.py
What a clean re-run looked like
calls completed 11/12 call failure rate 8% accuracy: all fields 100% (of calls that completed)

Good news on the surface — but the one failure's error string was InstructorRetryException: 504 DEADLINE_EXCEEDED..., not the raw APIError the Phase 3 retry code was written to catch.

The bug — mocked at the wrong boundary

_is_transient_provider_error checked isinstance(exc, APIError). Instructor's own internal retry loop catches every exception from the real API call and re-raises it as InstructorRetryException(...) from original_error — .create() never raises a bare APIError. Confirmed by mocking one layer deeper than the tests did:

with patch.object(_raw_client.models, 'generate_content', side_effect=err): _call_llm('test') Exception seen by caller: InstructorRetryException Is APIError? False __cause__ type: APIError · code: 504

The Week 2 tests had mocked _client.create directly — one layer higher — which raises whatever you tell it to, unwrapped. That mock was internally consistent and completely unlike reality.

The fix
def _is_transient_provider_error(exc):
    if isinstance(exc, APIError) and exc.code in _TRANSIENT_CODES:
        return True
    cause = exc.__cause__
    return isinstance(cause, APIError) and cause.code in _TRANSIENT_CODES
A second bug this exposed, in main.py

An exhausted transient error and a genuine shape failure both raise InstructorRetryException — so a real, retried-3x, still-failing 503 was landing in the same branch as "the model gave bad output," and being reported to the caller as 422 instead of 503. Fixed by checking exc.__cause__ inside that one except block before deciding the status code.

tests/test_service_retry.py::test_transient_codes_are_recognized_via_the_wrapped_exception PASSED tests/test_api.py::test_enrich_returns_503_when_a_transient_provider_error_exhausts_retries PASSED 30 passed — this time against the exact exception shape confirmed live

Nothing here needed a second LLM provider, a bigger retry library, or more code — the fix is two lines. The lesson is the mocking boundary: a mock one layer off from reality can pass every test in the file and still test nothing real.

WEEK 3 · D2 Teaching the model its own past decisions

The problem, from Phase 1's own eval

Nothing forces the model to classify the same kind of merchant the same way twice, and it has no memory of a local/unusual merchant it wasn't trained on. The fix chosen deliberately does not add a vector database — Phase 2 already persists every enrichment in SQLite. That table already is a knowledge base; it just needed a vector on each row and a similarity search.

Not cosmetic — the task_type asymmetry

Gemini's embedding model optimizes "this will be searched for" (RETRIEVAL_DOCUMENT) differently from "this is doing the searching" (RETRIEVAL_QUERY). Using the same task_type for both doesn't error — it just quietly produces worse similarity scores, which is a much harder bug to notice than a crash.

Graceful degradation — proven, not assumed

Both embedding calls in _enrich_and_persist sit inside their own try/except. RAG is layered on top of a working system — if the embedding API is down, /enrich still returns its normal result, just without extra context.

A loose end noticed, not chased down

The Uber query above actually retrieved two seeded rows above the 0.70 floor — Uber and the unrelated Chaiwala row — not just the Uber one. WEEK 4 A rate limiter with an injectable clock
rate_limiter.py (new) · config.py · main.py · tests/test_rate_limiter.py (new) · tests/test_api.py
The mechanism

A sliding-window counter over two independent windows at once — 60 seconds and 86400 seconds — each backed by a deque of call timestamps. Stale entries are evicted from the front before checking whether there's room for one more. A call must clear both windows to be allowed.

def acquire(self) -> None:
    now = self._time_fn()          # <-- injectable; real code passes nothing,
    with self._lock:               #     tests pass a fake clock
        self._minute.evict_stale(now)
        self._day.evict_stale(now)
        if len(self._minute.calls) >= self._minute.limit:
            raise RateLimitExceededError("per_minute", self._minute.retry_after(now))
        if len(self._day.calls) >= self._day.limit:
            raise RateLimitExceededError("per_day", self._day.retry_after(now))
        self._minute.calls.append(now)
        self._day.calls.append(now)
Why an injectable clock, not time.monotonic() called directly inside the class

A test proving "the 60-second window resets" would otherwise need to time.sleep(60) for real — slow, and a bad trade for one assertion. A FakeClock the test controls directly makes that assertion take milliseconds, deterministically, every run.

WEEK 4 Correlation IDs — and a filter that quietly did nothing
correlation.py (new) · main.py · tests/test_correlation.py (new)

A request now fans out across several internal calls — RAG retrieval, the rate limiter, the generative call, a DB write. correlation.py is the Python equivalent of the ticketing-platform track's CorrelationIdFilter: a contextvars.ContextVar holds the current request's id, and a logging.Filter stamps it onto every log line.

No explicit cleanup, and that's correct — not an oversight

Java's version needs finally { MDC.remove() } because thread-pool servers reuse worker threads across requests — skip it and one request's id leaks into the next one on the same thread. Starlette runs every request in its own asyncio Task, and a ContextVar.set() inside one Task is invisible to any other concurrently running Task. Same isolation guarantee, opposite reason: no shared, reused execution context to leak across in the first place.

A real bug, caught by actually running it

First attempt: logging.getLogger().addFilter(CorrelationIdLogFilter()). Read as obviously correct, imported cleanly — and would have raised KeyError: 'correlation_id' on the very first logger.info() call from any module other than main.py itself, which is nearly every log line this project has ever written.

$ python -c " import narration_enrichment.main as main main.logger.info('hello from a child logger') " --- Logging error --- KeyError: 'correlation_id' ... reproduced BEFORE the fix, on purpose, not assumed from reading docs

Why it breaks: Logger.handle() checks self.filter(record) using only the filters on the logger that originated the call. Propagation to an ancestor logger calls that ancestor's handlers directly — it never calls the ancestor's .filter() a second time. A filter added to the root logger only ever fires for messages logged directly via the root logger. The fix: attach it to the handler instead — Handler.handle() checks its own filters for every record that reaches it, regardless of origin.

$ python -c " import narration_enrichment.main as main import narration_enrichment.correlation as c c.set_correlation_id('test-child-logger-123') main.logger.info('hello from a child logger') " 2026-09-17 11:19:33 INFO [test-child-logger-123] narration_enrichment.main hello from a child logger
Confirmed live end to end, both directions
$ curl -i localhost:8123/health x-correlation-id: b5c9f14a-2057-4ce2-9868-537eaea6cf8e (generated) $ curl -i localhost:8123/health -H "X-Correlation-Id: my-custom-trace-id" x-correlation-id: my-custom-trace-id (echoed back, not overwritten)

The two regression tests for this deliberately build a private logger hierarchy rather than reusing the real root logger — by the time the test suite has imported main.py once, the real root's handler already carries the fix, which would silently mask the exact bug being tested for if reused.

P2 · D2 Chunker (pure) + PolicyDoc/PolicyChunk schema + Citation model
chunker.py (new) · models.py · db.py · tests/test_chunker.py (new) · tests/test_db.py · commit 6fedd43

Goal of the day: put in place the four boring pieces P2 will glue together — a chunker that splits a document, two tables to hold docs + chunks, and a Citation field on the response so /enrich can point at what it used. Nothing wired into the request path yet; that comes on Day 3 and Day 5.

chunker.chunk() is a pure function

Takes a string, returns a list of Chunk(index, content). No file I/O, no network, no DB. That's what lets the ingest orchestrator (Day 3) call it inside a database transaction without worrying about partial state on a raised exception — a pure function has nothing to roll back.

Fixed size + overlap, on purpose

500-char chunks with 50-char overlap. Semantic chunking is more sophisticated and could come later with numbers to justify it. Anti-overengineering rule from P1: SQLite over vector DB, cosine over numpy, and now: fixed-window chunker over semantic. Simplest thing that meets the current bar.

Loud validation at the boundary

overlap >= chunk_size would either infinite-loop (step of 0) or emit duplicates (negative step) — so we ValueError immediately instead of hanging or lying. Trust internal callers; validate at the external surface.

Chunks are frozen dataclasses

@dataclass(frozen=True) — a chunk is a value, not a container. Once the ingest layer has embedded a chunk, no downstream step can accidentally rewrite its content and desync the embedding.

Two tables + one Pydantic field

PolicyDoc: one row per ingested doc (doc_id PK, title, source_uri, sha-256 checksum, ingested_at). PolicyChunk: one row per chunk, with a JSON-encoded embedding column (same shape as EnrichmentRecord.embedding — same cosine loop in rag.py can walk both tables on Day 5). FK from PolicyChunk to PolicyDoc uses ON DELETE CASCADE + passive_deletes=True: deleting a doc removes its chunks in the database, without SQLAlchemy pre-loading every chunk row just to mark it deleted.

models.TransactionEnrichment.policy_citations: list[Citation] added with default_factory=list — Pydantic shares a class-level [] across instances the same way Python does. Ground truth for citations comes from the retrieval result on Day 5, not from anything the LLM produces.

SQLite gotcha caught in tests

SQLite ignores ON DELETE CASCADE unless you enable PRAGMA foreign_keys=ON per connection. The test fixture registers a @event.listens_for(engine, "connect") hook that flips it on for every checkout — otherwise the "delete cascades chunks" test would have silently passed for the wrong reason.

Unit-testable in isolation

13 chunker tests use plain string literals. 9 repo tests use real in-memory SQLite (StaticPool + FK pragma). No mocks of the pieces under test — mocking SQL semantics would just test the mock.

P2 · D3 POST /policies/ingest — idempotent by content-checksum
policy_ingest.py (new) · schemas.py · main.py · tests/test_policy_ingest.py (new) · tests/test_policy_api.py (new) · commit b72db22

Goal of the day: hand a policy doc's raw text to the service and have it end up as embedded chunks in the DB — once, no matter how many times the same doc is re-uploaded. The endpoint is the control plane for the policy corpus; the data plane (/enrich) doesn't consume any of this yet.

The whole ingest contract, in one flow
  1. sha256(content) — if the doc_id already exists with the same checksum, return {unchanged: true} immediately. No embedding budget spent, no chunk work redone.
  2. Chunk the text (pure function from Day 2).
  3. Embed every chunk one by one via rag.embed_text with task_type=RETRIEVAL_DOCUMENT — same asymmetry rule the past-narration RAG already follows.
  4. Atomic upsert: delete old chunks for this doc_id + insert the new set + update the doc row's metadata, all in one transaction. A concurrent /enrich sees the old chunk set OR the new — never a half-swapped state.

If ANY embed fails, the whole thing aborts

Contract enforced in the ingest service: no partial-embed state ever lands. A half-ingested doc would silently degrade retrieval (some chunks findable, some not, no signal). Losing an embedding budget on the first N chunks of a failed ingest is the cost of that guarantee — worth it.

Three failure codes, chosen deliberately

422 — Pydantic min_length rejects empty body before the service runs. 400 — a whitespace-only body passes Pydantic but the chunker returns [] (a caller bug worth surfacing). 503 — the embed provider is down; abort, tell the caller to retry, same shape as /enrich's own provider-error path.

No rate limiter on this route

Deliberate. The 20 requests/day cap exists to protect /enrich from being starved. If ingest shared that quota, one big-corpus upload would eat every enrichment slot for the day. Ingest is a rare, planned control-plane op; it's off the shared quota on purpose.

DELETE is idempotent

DELETE /policies/{doc_id} returns 204 whether the doc existed or not. Callers running a "wipe-and-reingest" loop don't have to special-case the first pass. Chunks cascade automatically via the FK from Day 2.

Test-file collision, fixed with a fixture

Both test_api.py and test_policy_api.py set app.dependency_overrides[get_db] at module scope. Pytest imports every module before running any test, so whichever loaded last silently stole the other's DB. Fix: install/restore the override in an autouse function-scoped fixture in test_policy_api.py. Now regardless of import order, each test runs against its own module's engine. Small pytest-isolation gotcha, worth remembering.

Goal of the day: make the raw policy doc live in a durable, addressable store — S3 — while the chunks + embeddings stay in SQLite for fast retrieval. Losing SQLite is now annoying (rebuild by re-running ingest against each S3 doc); losing S3 is real data loss. The storage split earns its keep here.

Standing rule reconfirmed in-turn: AWS resources are Rajat's

Dev works without S3

Leave POLICY_S3_BUCKET empty in .env and ingest skips the upload cleanly, records source_uri=None. Every existing test still passes without touching AWS. Setting the bucket turns the S3 path on for that deployment; no code changes needed.

Deterministic S3 keys

Same doc_id → same key (policy-docs/{doc_id}.txt). Re-ingest overwrites in place. No orphan versions accumulating on the second, third, tenth re-upload — one doc_id, one durable object.

Upload before embed, on purpose

S3 upload first, then embed calls. If S3 is down we bail early with 503 — no wasted embedding budget on a doc that would have ended up sourceless anyway. If S3 succeeds but embed fails, we've left at most one orphan S3 object per failed ingest (sweepable later); no half-embedded chunks in SQLite.

Delete cleans both stores best-effort

DELETE /policies/{id} removes the DB row (chunks cascade) then attempts the S3 delete. If S3 is down at delete time, the DB row is already gone and the S3 object becomes a sweep-later orphan rather than blocking the delete. Availability of the delete matters more than tidiness of S3.

Testing AWS without AWS — the moto pattern

@mock_aws (from moto) intercepts every boto3 S3 call inside the decorator and serves it from an in-memory fake. The code under test is real boto3.client('s3').put_object(...); the network never wakes up. In tests we set fake AWS_ACCESS_KEY_ID=testing/AWS_SECRET_ACCESS_KEY=testing just so botocore's credential resolution stops looking for real ones. The lru_cache on the S3 client needs a _reset_for_tests() hook so a client built before @mock_aws starts doesn't leak into a mocked test.

P2 · D5 Policy retrieval + prompt weaving + earned-not-decorated citations
rag.py · service.py · main.py · models.py · tests/test_policy_retrieval.py (new) · tests/test_api.py

Goal of the day: switch /enrich on to the policy corpus. Every call now embeds the narration once, searches BOTH the past-narration table AND the policy-chunks table, folds the two hits into a two-block prompt, and — the critical part — writes policy_citations on the response from the actual retrieval result, not from anything the LLM claims to have cited.

One embed call, two searches

The embed step is the slowest thing in the pipeline. So _enrich_and_persist embeds the narration ONCE (as RETRIEVAL_QUERY) and reuses that vector for both rag.find_similar_examples(db, query_embedding) and rag.retrieve_policy_chunks(db, query_embedding). Two independent embed calls would double the latency and burn twice the quota per /enrich.

Two labeled prompt blocks, not one merged wall of text

The past-narration block is labeled "similar past classifications" (guidance / evidence). The policy block is labeled "applicable policy excerpts from trusted policy docs" with "treat these as rules." Prompt-wise, past classifications are evidence and policy chunks are authoritative — the label difference is one lever we have to nudge the model to treat them that way.

Two independent degrade paths

Past-narration retrieval and policy retrieval each sit in their own try/except. If the embed call itself fails, both are skipped (they share the query embedding, so a dead embed kills both together). If one search raises but the other succeeds, that one still flows into the prompt. RAG is an enhancement, not the critical path — same rule as Week 3.

Policy floor 0.65 vs past floor 0.70

Policy chunks are shorter and more abstract, so the cosine score is inherently a bit lower even when a chunk is clearly relevant. Both floors were picked by eye — Day 6 (eval extension) will surface real numbers to tune them with.

Signatures kept backward-compatible

enrich_narration(narration, context=None, policy_context=None) — both context args are keyword-only with defaults, so test_service_retry.py's existing enrich_narration("some narration") calls still work unchanged. Adding P2 without breaking P1 tests was one of the small wins of the day.

The earned-citations rule (P2_DESIGN §6), enforced in code

After the LLM call returns, _enrich_and_persist does this — unconditionally, overwriting whatever policy_citations the model's function-calling might have populated:

result.policy_citations = [
    Citation(doc_id=chunk.doc_id, chunk_index=chunk.chunk_index,
             snippet=chunk.content[:280], similarity_score=score)

The model gets to choose the classification. It does NOT get to choose what to cite. P3 · D2 API key auth — hashed at rest, timing-safe, existence-hiding
auth.py (new) · db.py · scripts/create_api_key.py (new) · tests/test_auth.py (new)

Goal of the day: stand up the auth layer FIRST, before any /chat route exists. Everything P3 ships from here on depends on this — waiting until Day 4 to bolt it on is how "add auth later" turns into "we shipped an unauthed API to prod."

Bearer header, hashed at rest, same-error-for-both-failures

Clients send X-API-Key: <raw>. Server computes sha256(raw) and looks it up in the api_keys table — the raw key is never stored anywhere. A leak of the DB gives an attacker hashes to crack, not usable credentials.

Missing header AND wrong key both return 401 with the identical body {"detail":"API key missing or invalid."} and the same WWW-Authenticate: ApiKey header. Distinguishing them lets an attacker probe for which of two error paths triggered — a classic timing/existence side-channel.

SHA-256 is enough here (not bcrypt/argon2)

Different threat model from passwords. Passwords are low-entropy human-chosen strings — you need the slow hash to make brute-force cost real time. API keys are 256-bit random from secrets.token_hex. Entropy already stops brute-force; slow-hashing adds ~100ms of CPU per every chat request for zero security gain.

hmac.compare_digest, not ==

The == operator on strings short-circuits — runtime scales with prefix-match length, another side-channel. hmac.compare_digest is constant-time regardless of where the mismatch happens. Used defensively even after the DB PK lookup, so a future refactor that accidentally introduces == is caught by an audit reader.

CLI-only key creation, not an HTTP endpoint

scripts/create_api_key.py --label ... mints a key, prints the raw value to stdout ONCE, writes only the hash. Exposing key-creation over HTTP is one of the most common early footholds — keeping it out of the API surface entirely in P3 is the simplest defense. Provisioning-over-HTTP lands in P7 with Secrets Manager.

Rejected keys log the hash PREFIX, never the raw

Server-side observability needs to know which key failed. Logging the full hash lets a leaked log correlate to a leaked key; logging the raw is a live credential in log storage. First 8 chars of the hash is enough to match a specific key without either mistake.

Not committed, not committable

The auth code generates raw keys at runtime with secrets.token_hex(32) — 256 bits of entropy per call. No API key is baked into the codebase. The .env file is gitignored and was never tracked in any commit. The .env.example holds only a truncated placeholder (AIza...) as a comment about shape. Verified in-turn by grepping the full repo history for real key patterns; zero matches.

  • DELETE /chat/{session_id} → 204 idempotent, cascades to chat_turns via FK.

UUIDv4 session_ids, not autoincrement ints

Session ids are exposed in URL paths (/chat/{id}/message). An autoincrement int would let an attacker enumerate valid ids by trying 1, 2, 3, ...; UUIDv4 gives ~122 bits of unguessable state, so guessing is not a practical attack anymore. The regression test test_create_session_returns_uuid_and_persists_row asserts on the 36-char hyphenated shape — a future refactor to int ids fails it.

Same 404 for "not there" and "not yours"

get_chat_session_owned_by returns None for BOTH cases, and the route surfaces the same 404 body {"detail":"Session not found."} either way. Distinguishing the two lets an attacker who knows any session id (from a leaked log) enumerate other keys' access by watching status codes. The regression test test_send_message_to_someone_elses_session_returns_same_404_generic encodes this rule byte-for-byte.

DB-level CHECK on the role enum

chat_turns.role has a CHECK(role IN ('user', 'assistant')) constraint. Enforcing the enum at the DB level means a bug in one of the write paths CAN'T silently write "system" or an empty string — SQLite rejects it. Same defense-in-depth as P2's payments.status and payments.method CHECK constraints on the ticketing track.

User turn persists BEFORE assistant turn is generated

Order: user message → persist user turn → compute assistant reply (stub echo today, LLM tomorrow) → persist assistant turn + bump last_active_at — all in the same request handler. Turns get sequentially ascending ids, so ORDER BY id in list_chat_turns is a real chronological order, not a heuristic on timestamps.

The stub answer has a distinctive prefix on purpose

The Day-3 echo returns strings like "[stub-echo] Received 24 chars — Day 4 will wire the real LLM." If this stub ever leaks past Day 4's swap into a production response, the prefix makes it obvious in logs immediately. A less distinctive placeholder ("thanks for your message") could plausibly pass QA on a demo call.

5 Dockerfile Recipe for building the image

Read top to bottom — each line either sets up the environment or copies something in. Order matters here more than in normal code.

LineWhat it does
FROM ghcr.io/astral-sh/uv:...Start from an image that already has Python 3.11 and uv pre-installed — no separate install step needed.
WORKDIR /appEvery following instruction runs inside /app from here on.
COPY pyproject.toml uv.lock ./Copy only the dependency manifest first — not the code yet.
RUN uv sync --frozen --no-install-project --no-devInstall exactly the locked dependency versions. --no-dev skips pytest — this is a runtime image. --no-install-project skips our own code — it isn't copied in yet.
COPY src ./srcNow bring in the actual application code.
RUN uv sync --frozen --no-devRun again — this time it also installs our own package, now that the code exists.
EXPOSE 8000Documentation only — says "this container listens on 8000." The real port mapping happens in compose.
CMD ["uv","run","uvicorn",...,"--host","0.0.0.0",...]What runs when the container starts. 0.0.0.0, not 127.0.0.1 — otherwise nothing outside the container could reach it.

Why two COPY+RUN pairs instead of one: Docker caches each step. Dependencies rarely change; code changes constantly. Splitting them means an ordinary code edit skips the slow dependency-install step entirely — Docker reuses the cached layer from before.
