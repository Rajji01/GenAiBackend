01 Layered architecture & separation of responsibilities
BackendApplication.java · ProductSeedConfig.java
Concept

Controller handles HTTP concerns only, Service owns business logic and transaction boundaries, Repository owns persistence. Nothing above the Service layer should know SQL exists; nothing below it should know HTTP exists.

Why it's a real problem

Mixing concerns doesn't just look messy — it breaks tooling. A stray @Bean seeding demo data lived directly on the @SpringBootApplication class; it needed a JPA repository that a web-layer slice test deliberately excludes, so the whole test context failed to load. The bug wasn't the seed data — it was where it lived.

How we implemented it

Moved the seeding logic into its own @Configuration class (ProductSeedConfig, later ReferenceDataSeeder) next to the feature it belongs to. BackendApplication now does exactly one thing: SpringApplication.run(...).

Before
@SpringBootApplication
class BackendApplication {
  @Bean CommandLineRunner init(ProductRepository r)
}
VS
After
@Configuration
class ProductSeedConfig {
  @Bean CommandLineRunner seedProduct(...)
}
Rehearse this
Q: Why did a @WebMvcTest fail because of a completely unrelated bean?
A: @WebMvcTest slices the context to web-layer beans (controllers, @ControllerAdvice, converters, filters) — but it does not filter out plain @Bean methods declared directly on the @SpringBootApplication class, because that class is used as the test's configuration source regardless. Any dependency that bean needs must also be satisfiable in the slice, or the whole context fails to start.
Q: How do you decide what belongs in the "service" layer versus the "controller"?
A: If it would still make sense with no HTTP involved at all (a batch job calling the same method, say), it's a service concern. Status codes, @Valid, @PathVariable — those only make sense next to HTTP, so they stay in the controller.
02 Database schema consistency — Flyway over ddl-auto
V1__baseline_schema.sql · application.properties
Concept

Someone — a person or Hibernate — has to own "what does the schema look like right now, and how did it get that way." Flyway makes that owner an ordered, checked-in list of SQL files instead of whatever ddl-auto happened to do at some point in the past.

Why it's a real problem

The project's ddl-auto was commented out, but the tables already existed — created by Hibernate at some earlier point, then never touched again. A brand-new environment (a teammate's laptop, CI, prod) pointed at an empty database would have nothing. It "worked" purely because one machine had leftover state.

How we implemented it

V1__baseline_schema.sql mirrors the real, already-running schema exactly (verified with SHOW CREATE TABLE). Existing databases are baselined at V1 (spring.flyway.baseline-on-migrate=true) so Flyway treats V1 as already applied there; a brand-new empty database runs V1 for real. Hibernate is set to ddl-auto=validate — it now only checks the mapping matches the schema, it never changes anything.

Before
# spring.jpa.hibernate.ddl-auto=update
(commented out — undefined behavior)
VS
After
spring.jpa.hibernate.ddl-auto=validate
spring.flyway.baseline-on-migrate=true
Rehearse this
Q: Why not just set ddl-auto=update and move on?
A: update works for a solo sandbox but has no history, no review step, and no way to know what changed between two deployments. Flyway migrations are ordered, versioned files — you can read a diff of exactly what changed, and the same file runs identically everywhere.
Q: What does "baseline" actually do?
A: It tells Flyway "assume schema version N is already applied here, don't try to run it" — for a database that already has the tables from before migrations existed. It's how you adopt Flyway into a project without touching data.
Q: How did you prove it actually worked, not just "looked right"?
A: Ran the test suite twice — once against the existing ufcmain (baseline path) and once against a brand-new empty database created just for the test (real-migration path). Both booted clean and passed Hibernate's validate check.
03 DTOs instead of exposing JPA entities
dto/WeightClassRequest.java · dto/WeightClassResponse.java
Concept

The entity is the database's shape. The DTO is the API's shape. They look similar today and will not stay that way — the moment they diverge, only one of them is allowed to break client contracts, and it isn't the API.

Why it's a real problem

Two concrete failures, not hypothetical ones: (1) the write endpoint accepted a raw entity, so a client could set weightClassId itself — over-posting; (2) the read endpoint returned entities with a lazy @OneToMany fighters relation. The moment that list actually had rows and Jackson tried to serialize it outside the transaction, that's a live LazyInitializationException, not a style complaint.

How we implemented it

Java records for both directions — WeightClassRequest only exposes fields a client should set, WeightClassResponse only exposes fields a client should see. The service maps explicitly in both directions; nothing is ever handed through unmodified.

Before
@PostMapping
ResponseEntity<WeightClass> add(
  @RequestBody WeightClass wc)
VS
After
@PostMapping
ResponseEntity<WeightClassResponse> add(
  @Valid @RequestBody WeightClassRequest r)
Rehearse this
Q: What's "over-posting" and how did you prove it was fixed?
A: Sending fields the client shouldn't control — I POSTed a body with an explicit weightClassId: 999. Since the request record doesn't declare that field at all, Jackson silently drops it; the server generates its own id regardless of what arrives.
Q: Records or plain classes for DTOs — why?
A: Records are immutable, give you equals/hashCode/toString for free, and the constructor is the validation surface Bean Validation annotates directly. A DTO has no business being mutable — it's a one-shot data carrier.
04 Bean Validation, including cross-field rules
dto/WeightClassRequest.java · dto/BetRequest.java
Concept

Declarative constraints (@NotBlank, @Positive...) run before a single line of your business logic executes, and fail with a consistent shape every controller shares for free.

Why it's a real problem

Without it, invalid input — blank names, negative weights, a max-weight lower than the min-weight — goes straight to the database, or crashes somewhere unpredictable downstream instead of failing loudly and immediately at the boundary.

How we implemented it

Field-level annotations for the simple cases. For the one rule that spans two fields (maxWeight > minWeight), a plain method annotated @AssertTrue — no custom annotation class needed, Bean Validation treats any isXxx()-shaped method as a constraint.

@AssertTrue(message = "maxWeight must be greater than minWeight")
public boolean isWeightRangeValid() {
    if (minWeight == null || maxWeight == null) return true; // let @NotNull report it
    return maxWeight > minWeight;
}
Rehearse this
Q: Why guard the @AssertTrue method against nulls instead of just comparing the two fields?
A: If minWeight is null, a direct comparison either NPEs or reports a confusing second error on top of the @NotNull failure that's already the real story. Returning true lets @NotNull own that message instead of stepping on it.
Q: Where do you draw the line between Bean Validation and a service-layer check?
A: Bean Validation is for shape — is this field present, in range, well-formed. The moment a rule needs a database lookup — "does this fighter actually belong to this fight" — that's a service-layer concern with its own exception type, not a validator.
05 Global exception handling & a consistent error contract
exception/GlobalExceptionHandler.java
Concept

One @RestControllerAdvice maps exception type to HTTP status, once, for the whole app. Every error response is the same shape (RFC 7807 ProblemDetail): type, title, status, detail, instance.

Why it's a real problem

ProductController used to try/catch two exception types per endpoint, with a catch-all that leaked ex.getMessage() straight to the client. That pattern doesn't scale past one endpoint, and a raw internal message reaching a client is an information leak, not just untidy code.

How we implemented it

Custom, unambiguous exceptions (ResourceNotFoundException → 404, ConflictException → 409, InvalidRequestException → 400) instead of reusing IllegalArgumentException/IllegalStateException for everything. A generic Exception.class handler logs the full stack trace server-side but returns only "An unexpected error occurred" to the client.

400 → InvalidRequestException / validation 404 → ResourceNotFoundException 409 → ConflictException / OptimisticLockingFailureException
Rehearse this
Q: Why write ResourceNotFoundException instead of reusing IllegalArgumentException?
A: Type-based dispatch only works if the type means one thing. IllegalArgumentException gets thrown all over the JDK and third-party code for reasons that have nothing to do with "404" — reusing it for that meaning means some unrelated bug could accidentally return a 404 that makes no sense.
Q: Why hide the real message on a 500 but not on a 404 or 409?
A: A 404/409's message is something the caller caused and needs to see to fix their request. A 500 means something we didn't anticipate — the message might contain a table name, a stack frame, a query — none of which is the client's business, but all of which is exactly what you want in the server log.
06 Logging over System.out
BackendApplication.java · GlobalExceptionHandler.java
Concept

SLF4J gives you levels, structured placeholders, and a single switch to redirect or silence output per environment. System.out.println gives you none of that.

Why it's a real problem

A print statement can't be filtered by severity, can't be shipped to a log aggregator distinctly from stdout noise, and can't be turned off in production without a code change and redeploy.

How we implemented it

Every System.out.println in request/startup paths replaced with an SLF4J Logger. The level is chosen deliberately: expected client errors (404/409) log at warn, truly unexpected exceptions log at error with the full stack trace.

Rehearse this
Q: Why warn for a 404/409 but error for a 500?
A: warn means "a client did something we already expect and handle" — noisy but not actionable at 3am. error means "something happened we didn't design for" — exactly what should page someone or show up first in a log search during an incident.
07 Externalized configuration & secrets
application.properties
Concept

Config that differs by environment — and anything sensitive — lives outside the source file, read at startup from the environment.

Why it's a real problem

The DB password was committed in plaintext. It happened to be harmless here (no real secret, no shared repo at the time), but the pattern is the actual bug: whatever value sits there ships to everyone who can read the file, forever, in every clone.

How we implemented it

${DB_USERNAME:root} / ${DB_PASSWORD:rajat} — Spring property placeholders that read from the environment first, falling back to a value that only exists so this one dev machine keeps working without extra setup.

Rehearse this
Q: If there's still a fallback value, did you actually fix anything?
A: The mechanism is fixed — set the env var anywhere else (CI, staging, prod) and the fallback is never consulted. The fallback is a deliberate, documented dev-only convenience, not a hidden default a real deployment would silently inherit.
Q: Is the JDBC URL a secret the same way the password is?
A: No — a hostname/port/db-name is topology, not a credential; the actual risk (account takeover) sits entirely with the password. It's still worth externalizing for portability across environments, but for a different reason than the password.
08 Constructor injection, consistently
WeightClassController.java · ProductService.java
Concept

Dependencies come in through the constructor, not @Autowired field injection. With exactly one constructor, Spring wires it automatically — @Autowired on it is dead weight.

Why it's a real problem

Field injection can't be unit-tested without a Spring context or reflection tricks — there's no constructor to hand a mock to. It also hides an "unconstructable" class: if a class needs ten dependencies, a constructor with ten parameters is an ugly, honest warning sign; field injection quietly hides that cost.

How we implemented it

Lombok's @RequiredArgsConstructor on every controller/service, generating a constructor over the class's final fields. Dead, commented-out constructors and stray @Autowireds removed wherever they'd been left behind.

Rehearse this
Q: What does constructor injection buy you at test time, concretely?
A: `new WeightClassService(mockRepository)` — a unit test builds the object directly, no Spring context, no reflection, no @InjectMocks magic. Field injection can't be constructed that way at all from outside the container.
09 API documentation — and a real dependency-version bug
pom.xml
Concept

springdoc-openapi generates an OpenAPI spec and Swagger UI directly from the controllers and DTOs already written — no separate spec to keep in sync by hand.

Why it's a real problem

Undocumented APIs force every consumer to read controller source to know what's callable. But adding the dependency surfaced a sharper lesson: version 2.6.0 compiled fine and then threw NoSuchMethodError on ControllerAdviceBean.<init> at runtime — it was built against an older Spring Framework than the one Spring Boot 3.4.3 actually ships (6.2.3).

How we implemented it

Bumped to 2.8.3, confirmed /v3/api-docs and /swagger-ui/index.html both serve correctly against the real running app — not just "it compiled."

Rehearse this
Q: Why didn't the compiler catch a mismatched method signature between two libraries?
A: Both libraries compiled fine independently — the method existed when springdoc 2.6.0 was built. The mismatch only exists at the exact combination used at runtime: a newer Spring Framework removed/changed a constructor springdoc's compiled bytecode still calls. javac never sees both jars' assumptions collide; the JVM does, at the first call site that hits it.
Q: What's the general lesson for picking a third-party dependency version?
A: Check the library's stated compatibility with your actual Spring Boot version, and verify with a real run, not just a compile — a version mismatch across transitive framework dependencies is a runtime-only failure.
10 The testing pyramid, and the slice-test bug it caught
WeightClassServiceTest · WeightClassControllerTest · BackendApplicationTests
Concept

Three different sizes of test, each loading a different amount of the app: a plain unit test (no Spring at all), a web-layer slice (@WebMvcTest — controllers + advice + Jackson, service mocked, no DB), and a full integration test (@SpringBootTest — everything, real DB).

Why it's a real problem

Each size catches a different class of bug. A unit test can't catch a wiring problem because it never wires Spring. Sure enough: the very first @WebMvcTest we wrote failed to load its context at all — a slice-only bug a unit test structurally cannot see, and only a slightly different full-context test would even reveal.

How we implemented it

WeightClassServiceTest — Mockito, no Spring, tests only the DTO↔entity mapping. WeightClassControllerTest — @WebMvcTest, proves the actual HTTP contract (status codes, field-level validation errors) with the service mocked out. BackendApplicationTests — full boot against real MySQL, the only one that would have caught the Flyway/Hibernate wiring being wrong.

Rehearse this
Q: Given the three sizes, which one would catch a bad SQL migration? Which would catch a wrong HTTP status code? Which would catch a typo in a service method?
A: Migration — only the full @SpringBootTest (it's the only one touching the real DB). Status code — the @WebMvcTest slice (fast, no DB needed to prove the contract). Service typo — the plain unit test, fastest of all three and the one you'd want running on every keystroke.
Q: We didn't add @DataJpaTest or Testcontainers this round — was that the right call?
A: Given what actually changed (mapping and status codes, no new custom @Query), yes — the existing full-context test already exercises the real schema. Testcontainers would earn its cost once we're writing repository-specific queries worth testing in isolation from the rest of the app.
11 Optimistic locking & the lost-update problem
entities/Bet.java · BetService.java · BetConcurrencyTest.java
Concept

A @Version column lets Hibernate add AND version = ? to every UPDATE. If the row's version moved since you read it, zero rows match, and Hibernate raises ObjectOptimisticLockingFailureException instead of silently overwriting someone else's write.

Why it's a real problem

Two users load the same bet, both change the amount, both save. Without a version check, whichever UPDATE runs second simply wins — the first user's change vanishes with no error, no log, no trace. That's a lost update, and it's silent, which is what makes it dangerous.

How we implemented it

Added @Version private Long version; to Bet via a real migration (V2__add_bet_version.sql, since the column didn't exist before). updateBetAmount reads, mutates, saves — no manual locking code; Hibernate does the version check for free on every save. GlobalExceptionHandler already maps the resulting exception to 409 Conflict.

sequentialStaleReads → deterministic, no threads trueConcurrentUpdates → real ExecutorService race live curl race → one 200, one 409
Rehearse this
Q: Why does a test with no threads at all prove the same thing as a real two-thread race?
A: Optimistic locking checks one fact at commit time — does the version I'm writing against still match the row's current version. It has no idea whether the staleness came from true parallel threads or from two sequential reads in a single-threaded test; the check is identical either way. That's what makes it a correctness property, not a timing-dependent behavior.
Q: Optimistic vs pessimistic locking — why optimistic here?
A: Betting reads a bet far more often than it's concurrently edited — most bets are placed once and never touched again. Pessimistic locking (SELECT ... FOR UPDATE) pays a lock-hold cost on every read whether or not a conflict was ever going to happen. Optimistic locking pays nothing until a real conflict occurs, which is rare here. It flips the other way for something like a single shared inventory counter under constant contention — many writers, few readers — where pessimistic locking (or an atomic decrement) avoids paying for repeated failed retries.
Q: The API returns 409 and stops — should it retry automatically instead?
A: Depends on who has enough context to resolve the conflict. Here, the amount itself is what conflicted — the server doesn't know whether to keep User A's 100 or User B's 200, so surfacing it to the client to re-fetch and decide is correct. A server-side retry only makes sense when the retried operation is safely re-derivable from fresh state without a human choosing between two values — e.g. re-applying "decrement stock by 1" against whatever the current stock now is.
